# Olli 产品路线图

> 版本：0.42 · 日期：2026-08-06 · 状态：通用 Agent 路线已回正，当前处于既有基线收口与 Computer Use 可行性验证准备阶段

## 1. 产品判断

Olli 是一个原生 macOS 通用 Agent。用户用自然语言描述希望得到的结果，Olli 理解当前电脑状态，规划并选择合适能力，跨应用执行动作，重新观察和验证，再交付有证据的结果。

产品北极星是：

> 用户表达目标，而不是学习每个应用的操作步骤；Olli 在安全边界内完成电脑上的工作，并允许用户随时追问、修改、暂停或取消。

输入框写回仍是高频且必须可靠的能力，但它是 `Dictate` 快速路径和 Computer Use 的一个基础动作，不再代表整个产品的最终范围。当前产品与实施主线以[《通用 Agent 产品与实施路线》](通用Agent路线.md)为准。

产品对外名称已改为 Olli。现有 `Friday.xcodeproj`、Scheme、Bundle ID、`FRIDAY_*` 环境变量、钥匙串 service 和诊断目录暂时作为兼容标识保留，后续如迁移必须单独处理系统权限与本地数据连续性。

## 2. 目标用户与核心场景

### 目标用户

- 经常在多个应用之间切换的知识工作者。
- 需要写邮件、消息、任务、笔记，但不想反复整理措辞的人。
- 使用专业软件或复杂后台，遇到问题时需要屏幕上下文帮助的人。
- 希望用语音发起自动化任务、但不想学习终端和复杂工作流的人。

### 核心场景

- `Dictate`：在任意可编辑输入框中口述，整理后写回；找不到目标时交付可复制结果。
- `Conversation`：围绕当前问题或用户主动提供的屏幕选区自然对话。
- `Work`：打开应用、操作文件、浏览网页、跨应用搬运信息并验证结果。
- `External Side Effect`：先生成邮件、消息或表单草稿，用户确认后再发送或提交。

第一个通用 Agent 验收任务不是继续适配某个特定输入框，而是：打开 TextEdit、新建文档、写入固定内容、保存到指定测试目录，并通过文件内容或窗口状态读回验证。

## 3. 产品入口与共享执行核心

```text
Fn
-> Dictate 快速路径
-> 口述、整理、写回；不创建重型 Work

Control + Option
-> Conversation 前台
-> 直接回答，或把需要工具、等待、多步骤的目标提交为 Work

文字任务入口
-> 直接提交 Work

所有 Work
-> Planner -> Capability Router -> 执行器 -> 重新观察与验证
```

这些入口共享产品身份，但生命周期必须分开：

- `Dictate` 追求高频、低延迟、忠于原意和可撤销，不经过重型 Agent。
- `Conversation` 负责实时听说、直接回答和提交 Work，不持有后台执行循环。
- `Work` 负责可查询、可修改、可暂停、可取消的任务；语音断开不自动取消任务。
- `Agent` 不是某个入口或一次工具调用，而是 `Observe -> Plan -> Act -> Verify` 的执行核心。
- 可撤销本地动作默认自动执行；发送、提交、删除、购买和权限变化仍按风险确认。

## 4. 当前实现事实

已经存在：

- macOS SwiftUI App 工程。
- Talk 会话身份与用量账本已从界面编排中独立，单轮使用随机 Session ID 关联无内容诊断，并在会话结束后拒绝迟到用量写入。
- 每次 Talk 覆盖写入一份本地 JSONL 生命周期轨迹。每次用户说话、停说、回复请求、Response 开始、Assistant Item、首段音频、播放完成和工具解析都关联 Friday 自有 Turn/Response/Playback 身份，并分别记录阶段耗时；不包含音频、转写、回复文本、截图、Prompt 或密钥。
- Talk 已建立 Friday 自有的 Turn、Response、Assistant Item 与 Playback ID，并把 Realtime 的临时 `item_id` / `response_id` 映射到该身份链；旧轮次迟到的语音、音频和取消事件不会重新激活或停止当前轮次。
- Talk 的 Presentation 已从 Coordinator 抽出，灵动岛状态、实时声波和岛内提示通过单一接口映射；窗口只在状态切换时显示或重排，音频帧以最高 30fps 只刷新声波数据。
- Talk 的 Provider、音频端口、音频所有权、录制策略和启停已收敛到 `ConversationRuntimeSession`；`ConversationCoordinator` 不再根据供应商类型分别启动音频与连接。
- 当前产品组合仍只使用 `DirectRealtimeConversationRuntimeSession`：先启动 Friday VoiceProcessingIO/安全半双工音频，成功后连接现有 Realtime Provider，用户入口和界面行为不变。
- LiveKit 只完成零费用 Stage 0：短期 Room Credential、强制关闭录制、单一 Transport 音频所有权、Provider 事件映射和启动失败清理均有假实现契约；未引入 SDK、真实 Room、Agent 进程或生产开关。
- 单一类型化工作流状态，统一表达不可用、就绪、准备、录音、处理、写入、成功和可恢复失败。
- Live 就绪检查覆盖本地服务、OpenAI 网络、API Key 和配置模型，不创建 Realtime 会话。
- App 启动后顶部灵动岛常驻；点击紧凑态展开约 `520 x 300` 的主页，点击设置后在同一窗口内形变为约 `400 x 480` 的纵向菜单；外部点击、`Esc` 或收起按钮返回紧凑态。
- Friday 作为普通 Dock App 提供独立原生主工作台；关闭主窗口不退出进程，Dock 点击和灵动岛主页右上角的展开按钮会恢复同一个窗口。
- 灵动岛展开主页继续保留快捷操作、提示、失败、结果和用量入口，权限恢复、刷新、清除结果和退出仍可在岛内设置页完成。
- 单独按下并松开 `Fn` 后开始或结束转写；期间出现其他修饰键或普通按键时取消触发。
- `Control + Option` 修饰键组合，完整按下并松开后启动或结束语音 Agent；当前由 Talk Runtime 承载。
- 快捷键反馈使用内置本地 WAV：Dictate 采集前播放 `chime`、有效录音进入整理时播放 `sparkle`、Talk 采集前播放 `success`、Dictate Provider 处理失败时播放 `error`；采集前提示音有限播放并淡出后才移交麦克风，资源异常不阻断工作流。
- 空闲状态不采集麦克风、不运行 Speech 识别任务，也不创建 Realtime 凭证；Hey Friday 原型保留为未来可选模式，当前默认关闭。
- Talk 先在本地启动麦克风和播放引擎，成功后才申请 Realtime 凭证；连接期间最多缓存 5 秒开头语音。
- Talk 触发后先同步准备颜文字和声波，再显示灵动岛窗口，不显示空白首帧。
- Talk 从触发开始约 5 秒仍未检测到用户人声时只主动问候一次；只有 Provider 确认的 `speech_started` 会在生成前取消该问候，本地音量候选不会抢先改变对话状态。
- Talk 使用 `near_field` 降噪与 Provider 独占的 `semantic_vad`（`eagerness=auto`）。Provider 负责确认用户开始、停说、提交音频和自动创建回复；客户端正常回合不再发送 `input_audio_buffer.commit` 或 `response.create`。
- Dictate 和 Talk 默认都使用 `gpt-realtime-2.1`；Dictate 使用 `reasoning.effort=minimal` 和文本输出，Talk 使用 `reasoning.effort=low` 和音频输出。两者保留独立模型配置，便于以后单独迁移专用转写链路。
- Talk 提示词要求普通回答通常一句、最多两句，不复述用户请求、不介绍能力，也不重复“请告诉我需求”等填充语；工具调用前保持安静，收到写入成功回执后只说“写好了”。
- Talk 默认不设置额外 `max_output_tokens` 硬上限，普通回复、开场问候、工具跟进和 Work 结果语音都不由 Friday 额外截断。提示词要求先给核心结论并完整结束当前句子，若模型侧返回 `incomplete`，保留已播放内容并继续当前会话，不把整段 Talk 当作服务错误结束。
- 客户端分别记录快捷键激活、Presentation 显示请求、本地音量候选、Provider 人声开始/停止、Provider 自管回复、Response/Assistant Item 到首段音频、生成完成、播放完成和工具解析耗时，以及 `response.done.usage` 对应的估算费用；不记录用户语音或文本内容。
- Talk 优先启动直接基于 `VoiceProcessingIO` 的全双工音频，以实际扬声器播放作为系统 AEC 参考；Assistant 准备或播放期间，本地近场门只把持续且具有语音动态的候选连同预卷上传给 Provider。Provider `semantic_vad` 确认 `speech_started` 后，客户端才显式取消并截断当前回复；Provider 自动取消保持关闭。初始化失败时自动退回不接受播放期插话的 AVAudioEngine 安全半双工。
- 音频设备配置变化会安全结束本轮 Talk、断开 Provider 并释放麦克风；后台就绪检查不再把活跃对话重置为休眠。
- 展开灵动岛底部提供退出命令，并支持 `Cmd+Q`。
- Accessibility 权限状态与用户主动授权入口。
- 通过系统级焦点、前台应用焦点、可编辑父控件和有限焦点后代查询，尝试锁定当前输入目标。
- Dictate 在键盘焦点未被 Web/Electron 应用暴露时，按指针当前位置精确命中可编辑 Accessibility 控件作为安全兜底；普通元素、密码框或无法解析时仍不写入。
- 输入目标不是录音前置条件；开始时没有目标仍继续，模型返回后会再检查一次当前焦点。
- 本地麦克风采集与实时音量计算，不保存音频文件。
- 录音状态在未达到可视声音阈值时显示八条等高短线；检测到声音后，每个 1024 帧音频分片被切成八段独立音量，并以绝对响度为主、分片内相对差异为辅。每条竖线使用 2pt 整点宽度与 2pt 整点间距，只把高度声明为动画值，避免亚像素抗锯齿造成的粗细错觉和逐帧跳动。
- 可视声音阈值为 `0.13`，低于实际模型语音判定阈值 `0.18`；轻声可以先触发界面反馈，但不会仅凭该较低阈值建立 Realtime 会话。
- 本地以 `0.18` 当前音量、`0.24` 峰值和 `0.08` 秒有效声音时长拦截静音录音；检测到有效声音后才建立 Realtime 会话，不向文字生成阶段提交无效内容。
- 静音录音结束后，在展开灵动岛内短暂显示“未收听到声音”，不创建模型响应且不抢焦点。
- 不抢输入焦点的顶部灵动岛，统一呈现空闲、录音、处理、失败、结果恢复和一次性提示；成功写入后回到常驻紧凑态。
- 灵动岛首次出现时从轻微缩小和透明状态柔和展开；展开矩形与屏幕顶部黑色区域衔接，底部使用 28pt 圆角。
- 灵动岛使用固定展开窗口、内部形变和系统刘海尺寸计算；紧凑态忽略鼠标事件，避免透明窗口遮挡原应用。
- 紧凑态使用等宽左右安全区，文字和状态动画分别居中；紧凑态本身忽略鼠标事件，由全局点击命中岛区域后展开，避免透明大窗口遮挡其他 App。
- 同一快捷键负责开始、结束和处理阶段取消；Dictate 只保留 10 分钟遗忘录音安全停止，不再用日常短时上限阻断测试。
- 正常启动时直接使用 Realtime；Mock Provider 仅通过开发环境变量启用，不出现在产品菜单中。
- 24 kHz 单声道 PCM16 麦克风转换和 Realtime WebSocket Provider。
- 录音浮层显示录音、整理和写回结果；未经最终校验的 Live 增量文本不直接外显。
- 忠实保留原意、清理口癖、自我纠正和结构化文本的非对话式听写提示词，明确要求问题只转写不回答、残句只保留不续写。
- 提示词定义专用无语音标记；最终解析器会拦截寒暄、就绪提示和确认式包装，并在已知确认模板中只恢复被引用的原始口述片段。
- 仅监听本机的短期凭证服务，长期 API Key 不进入客户端。
- 标准配置、诊断和启动命令只从 macOS Keychain 读取长期 Key，不受旧 Shell 环境变量覆盖；Security.framework 隐藏输入会完整保存长 Project Secret，支持原生弹窗、`Cmd+V` 和右键粘贴，配置后执行零推理模型元数据验证，检查失败也不会擅自删除已保存的 Key。
- 本地服务网络失败诊断与显式 HTTP 代理/TUN 联调路径。
- 本地服务不设置每日或累计会话上限；持久化签发数只用于诊断展示。
- 凭证签发保留默认每 60 秒最多 6 次的异常突发熔断；Talk 只在没有新用户输入时累计连续响应，并在 30 秒内达到 4 次时停止，新用户回合会立即清零，避免把正常快速多轮误判为风暴。
- 官方 `gpt-realtime` 已完成短期凭证、WebSocket 和单轮音频到文本的真实响应验证。
- 最近一次整理结果在写回失败时仍保留并可复制；token 用量只保留在开发诊断中。
- 没有可靠输入目标时展示完整转写结果、复制和关闭操作；写入失败时同一浮层还可重试写入。
- 处理失败时在内存中保留本轮音频，用户可以显式重试且不会自动重复消耗会话。
- 写入失败时保留最终文字和原目标，用户可以只重试写入而不再次调用模型。
- 密码输入框默认禁止写入；无法验证的粘贴只显示“已发送，请确认”。
- Debug 使用 Team `7WKP2RG3A9` 的稳定 Apple Development 签名。
- 通过 Accessibility 锁定和恢复目标焦点，再模拟 `Cmd+V` 写入原生、Web 和 Electron 输入框。
- 写回前记录目标解析来源和无内容的写回结果，便于区分目标缺失、焦点变化与粘贴事件失败。
- 剪贴板后备在未检测到用户新复制内容时恢复原剪贴板。
- 展开灵动岛主页展示当前状态、快捷操作、最近一次结果、Talk 回复/token/估算费用、最近 Dictate token 和本地签发数；设置形态展示完整权限、服务、额度、刷新、清除和退出项。
- Talk 进行时可以用 `Control + Command` 进入跨显示器区域框选；选择层不压暗屏幕，鼠标旁显示不会越过屏幕边缘的“拖动框选 / Esc 取消”指引，随后用户可以用“这个”“这句话”等自然指代继续提问。
- 区域图片只保存在内存中，不写入磁盘或普通日志；图片事件使用不超过 Realtime 32 字符限制的短 ID，并在服务端确认新图片后才替换上一张上下文。框选和图片确认期间的 Talk 音频会有界暂存，图片确认成功后再按原顺序发送给 Provider，由 Provider 在收到完整音频后独立判断端点。
- VoiceProcessingIO 主路径会把 AEC 处理后的连续 24 kHz PCM16 在收听期上传给 Provider；本地近场输入门仍运行，但只为声波和无内容诊断提供音量候选，不创建、结束或取消用户 Turn。
- `FRIDAY_TALK_ENDPOINTING=client_gate` 保留旧的本地断句与手工 `commit`/`response.create` 路径，只作为显式开发回退，不是产品默认。
- `wait_for_user` 只用于高置信度纯静音、极短非语言噪声或明显扬声器残留；持续或可辨认的人声必须直接回答，无法理解时简短澄清，不能因为意图或称呼不确定而静默。若 Provider 已测得用户人声持续至少约 700ms，客户端会确定性覆盖错误的静默工具调用并请求一句澄清。播放期只有 AEC 后通过本地持续人声候选门的音频才会上行，普通回声和瞬态噪声不会创建 Provider 用户 Turn。
- Talk 已定义可替换的 `UserTurnTranscriptionProviding`、`FinalUserTranscript`、健康状态和零费用 Mock/Unavailable 实现；Realtime 客户端可以解析官方最终输入转写完成/失败事件，并按 Provider `item_id` 关联到 Friday 自有 TurnID。
- 配置 final ASR 后，`submit_work` 只创建会话内 `WorkDraft`，不会直接进入后台队列。原任务 Turn 的最终转写和模型意图必须同时存在，用户再在独立确认 Turn 中明确说“确认提交”，本地校验通过后才创建正式 Mock Work；“好的”等模糊表达不会提交。final ASR 关闭时，后端隐藏依赖原话核对的 Work 工具，但仍保留 `wait_for_user` 和可撤销 `write_focused_input`。
- 任务草稿可以在提交前丢弃；会话结束时清除草稿和最终转写正文，后台已提交 Work 的观察与结果交付不受影响。
- `ActionProposal`、`ActionReceipt` 与带版本、方法校验和 64KB 上限的 RPC JSON 契约已落地。
- Realtime 的 `open_application(application)` 与 `write_focused_input(text, application?)` 已接入 `ConversationActionBridge`；Bridge 校验参数、生成低风险本地 ActionProposal，并按 Tool Call ID 缓存回执，避免重复启动或写入。
- 用户说出的应用名由本机运行进程、标准 Applications 目录中的已安装 Bundle、显示名、Bundle ID 和有限别名解析；当前 “Codex” 明确映射到 `com.openai.codex`，“微信”映射到 `com.tencent.xinWeChat`。显式应用优先于 Talk 启动时锁定的输入目标。
- 本地执行器接受 `localNavigation + permission.none` 与 `reversibleLocalWrite + permission.none`。指定应用写入会先启动或激活唯一应用、复验前台 PID，并有限等待 Accessibility 目标就绪；标准键盘焦点缺失时，只接受前台窗口中唯一的非密码可编辑控件，或前台同进程鼠标精确命中的可编辑控件。找不到应用、目标歧义、密码框、跨应用指针、多个候选、无可靠目标或焦点变化时不退回其他控件。执行结果区分 `succeeded/failed/unknown`，附带具体激活阶段码和辅助功能权限快照，且 Talk 不因动作结束。
- macOS 14.0 最低部署目标。

- `gpt-realtime-2.1` 的 Dictate 与 Talk 凭证签发、真实音频输入输出、延迟和当前 API Project 权限尚未真机验证；自动门禁只使用假上游，不消耗余额。

- 屏幕区域框选与 Realtime 图片上下文代码已实现；整窗捕获、模型主动请求截图和标注层尚未实现。
- 高风险 Agent 工具、账号体系、官方账户余额读取和正式 DMG 发布流程。
- 跨会话 Conversation History、滚动摘要、长期 Memory 和 Context Assembler。
- Talk 最终用户转写的真实 Provider 与生产启用、稳定 Thread 和带 revision 的 Realtime Bootstrap；当前仅完成中立契约、Realtime 事件解析和 WorkDraft 消费边界，默认配置仍不产生额外 ASR 费用。
- 具备真实外部副作用的 Work Runtime、通用 Capability Registry、高风险分级权限、远端 Action Transport 和持久化 Result Delivery；当前只有应用导航、可撤销输入框写入执行器、本地无副作用 Mock Work Runtime 与 Talk 工具桥接。
- LiveKit Swift SDK、真实 Room/Agent、真实 AEC/Adaptive Interruption、`gpt-realtime-2.1` 音频/图片/工具兼容性和真实费用对比；Stage 0 通过不代表这些能力已实现。

尚未真机验收：

- TextEdit、备忘录和 Safari 的跨应用写入。
- 单独 `Fn` 在内置键盘和外接键盘上的系统事件是否一致，且不会与系统表情、听写或功能键设置冲突。
- `Control + Option` 与 VoiceOver 及包含普通按键的系统快捷键是否能稳定区分，以及 Talk 启动和结束是否稳定。

- 有刘海、无刘海与外接显示器之间切换时，岛的内容是否始终避开不可显示区域并保持顶部居中。

- 微信等未直接暴露系统级焦点的应用能否通过前台窗口兼容查询稳定识别。
- 开始和结束时均无输入目标的情况下，完整结果浮层、复制和关闭交互是否符合预期。
- `Cmd+Z` 是否能在三个目标应用中恢复插入前内容。
- 权限拒绝、目标消失和焦点变化时是否始终停止写入。
- Live 模式的真实转写保真度、延迟、token 用量和错误恢复。
- 真实中文语音能否稳定把“写入 Codex”等应用意图转换为工具调用，并在 Codex、Xcode 和 Safari 中准确找到已聚焦输入框。
- 可撤销写入成功后是否只简短说“写好了”，失败后是否保持 Talk 连接，以及准备态是否始终使用静止粉色声波而不先闪灰色。

## 5. 阶段路线

以下 `Phase 0-5` 保留为项目从工程骨架、输入框、语音和屏幕能力逐步形成的历史记录，不再代表 2026-08-06 之后的开发顺序。当前开发必须按[《通用 Agent 产品与实施路线》](通用Agent路线.md)中的 Milestone 推进：先收口基线，再验证 Computer Use，随后打通单一 Planner 的垂直执行闭环，最后接入 Conversation、外部副作用、持久化和记忆。

不得因为下面某个旧 Phase 尚未达到“体验完美”就阻塞通用 Agent 验证，也不得用已有 `open_application` 或 `write_focused_input` 两个 Action 宣称 Phase 4 已完成。

### Phase 0：工程骨架（已完成）

目标：让项目能够在 Xcode 中打开、运行和持续迭代。

交付：

- Friday 后台常驻 App 可以启动并显示顶部紧凑灵动岛。
- Mock 开发模式不请求屏幕权限，也不产生 API 费用。
- Mock 文本链路可独立测试，不产生 API 费用。

退出条件：

- Xcode Debug 构建通过。
- 新机器打开项目后，产品名、Scheme、Bundle ID 一致。
- Mock 开发模式可以在没有 API Key 的情况下运行。

### Phase 1：通用输入框注入（MVP-1）

目标：先证明“说话后的内容能回到用户正在使用的输入框”。

当前状态：Phase 1A 和零成本 Phase 1B 代码已实现并通过 Debug 构建，等待真实 Mac 人工验收；未达到本阶段退出条件。

范围：

- 读取前台应用当前焦点元素。
- 按系统级焦点、前台应用焦点和可编辑父控件分层解析输入目标。
- 识别可编辑文本区域。
- 使用 Accessibility API 锁定触发前的输入框并在处理后恢复焦点。
- 使用剪贴板和模拟 `Cmd+V` 完成实际写入，以触发目标应用的真实输入事件和系统撤销。
- 首次使用时检查辅助功能权限；拒绝时显示原因和系统设置入口。
- 使用剪贴板后备时保存并尽量恢复用户原有剪贴板内容。
- 支持替换选中文本、插入光标位置和撤销。
- 无法可靠识别输入目标时不阻断录音；转写完成后展示完整结果并允许复制。
- 先验证 TextEdit、备忘录、Safari 搜索框。

退出条件：

- 三个目标应用都能完成固定测试文本注入。
- 常见原生、Web 和 Electron 输入框可以通过同一套目标解析流程识别。
- 键盘焦点未暴露时，指针正位于可编辑控件的场景可以通过严格命中兜底识别；指针不在可编辑控件时不会猜测写入。
- 找不到目标时不会误写到其他控件。
- 找不到目标时仍能完成转写，并在结果浮层中复制完整文字。
- 辅助功能权限被拒绝时不会尝试写入，并给出可恢复提示。
- 剪贴板后备完成后不会静默丢失用户原有剪贴板内容。
- 用户可以撤销或清除本次插入。
- 自动化测试覆盖目标解析的成功、失败和无焦点场景。

### Phase 2：实时语音改写（MVP-2）

目标：让用户用自然口语完成真实输入。

当前状态：本地录音、提示词、结构化 Provider、短期凭证服务、Realtime WebSocket 客户端和成本次数闸门已实现并通过签名 Debug 构建；真实 API 已完成短期凭证、`session.created` 和 4.19 秒合成语音到文本的受控验证，尚待用户麦克风与输入框写回真机验收。

范围：

- 使用统一的类型化工作流状态表达不可用、就绪、准备、录音、处理、写入、成功和可恢复失败。
- 只有辅助功能、麦克风、快捷键和语音服务均满足要求时才显示“已就绪”。
- 正式申请 Realtime 临时凭证前先验证麦克风权限和输入设备。
- 从系统设置返回或按快捷键时重新读取真实麦克风权限；已经授权时不展示过期的权限错误。
- 按住或按下快捷键开始录音，释放或再次按下结束本轮。
- Realtime Provider 接口和 Mock Provider 并存。
- 后端生成临时凭证，API Key 不进入客户端。
- 口语转为适合当前场景的邮件、消息、标题、列表或代码文本。
- 在本轮成功或用户取消前，将音频只保留在内存中；处理失败时支持无需重新说话的显式重试。
- 写入失败时保留生成文本和原目标，允许重新写入或复制，不悄悄丢失用户内容。
- 准备、录音和处理阶段支持用户取消；写入事件发出后不承诺可取消。
- 显示录音、处理、插入和失败状态。

退出条件：

- 一轮语音可以稳定得到文本并插入当前输入框。
- 本地语音服务停止时，Friday 在录音前显示不可用；服务恢复后无需重启 App 即可恢复就绪。
- 模型处理失败后可以使用内存音频重试，并且成功或取消后清除该音频。
- 写入失败不会报告成功，用户可以重试写入或复制结果。
- 断网、权限拒绝、服务错误都有可理解的恢复路径。
- 用户在系统设置中允许麦克风后，无需重启 Friday 即可恢复就绪，快捷键不会继续展示旧的权限提示。
- 日志不包含原始音频、完整屏幕截图、API Key 或完整敏感文本。
- 能记录每轮耗时和错误类型，但不记录用户内容。

#### 开发期成本监控与循环保险

- 产品正常启动默认使用 Realtime；零费用 Mock 只能通过开发环境变量 `FRIDAY_DICTATION_MODE=mock` 显式启用。
- 第一里程碑 Realtime 累计预算目标仍为 `$5`，但当前不做本地美元硬停机；Talk 已能估算本轮费用，权威总支出与余额仍以 OpenAI Platform 为准。
- 本地凭证服务不设置每日或累计签发上限；只记录本地签发数，并在默认 60 秒内出现 6 次凭证尝试时触发异常循环熔断。
- Dictate 输出只允许文本，`max_output_tokens` 保持 256；录音只保留 10 分钟遗忘停止，不再使用 30 秒日常测试上限。
- Dictate 不发送截图、不生成音频输出；它以 `gpt-realtime-2.1` 的 `response.done` 作为可写回结果，不等待额外输入转写。Talk 才按配置使用独立计费的 `gpt-live-transcribe`，采用 `minimal` delay；空模型环境变量可以关闭 Talk 的该通道。Talk 的用户主动框选和音频输出保持独立配置。
- 同一时间只允许一个 Response；创建 Response 后不自动重试。
- 从 `response.done.usage` 记录 token、估算费用、耗时和错误类型，不记录用户内容。
- 当前 Talk 模型 [`gpt-realtime-2.1`](https://developers.openai.com/api/docs/models/gpt-realtime-2.1) 的官方标准价格（2026-07-29 查询）为：文本输入 `$4/1M`、缓存输入 `$0.4/1M`、文本输出 `$24/1M`、音频输入 `$32/1M`、音频输出 `$64/1M` token；低 reasoning effort 仍可能产生额外推理 token，必须以真实 `response.done.usage` 为准。
- 官方换算为用户音频每 100ms 约 1 token、助手音频每 50ms 约 1 token；只计算音频时，用户说 30 秒约 `$0.0096`，Friday 说 30 秒约 `$0.0384`，多轮上下文和文本 token 另计。
- 每轮 Dictate 隔离或清理模型侧 Conversation，避免历史内容在后续 Response 中重复计费；这不等于删除未来由用户控制的本地 Conversation History。
- Talk 在没有新用户输入的情况下于 30 秒内连续完成 4 次响应时自动结束本轮；每个确认的新用户 Turn 都会清零计数，本地保护只阻断自主响应循环，OpenAI Platform 的项目预算仍是账户侧保护。

### Phase 3：屏幕上下文与指导

目标：用户明确请求时，Friday 能理解当前屏幕并帮助用户完成下一步。

当前状态：Phase 3A 的“Talk 中手动框选区域”已完成透明选择层、鼠标指引和图片确认边界的代码与零费用视觉检查；尚待真实屏幕权限、真实区域内容和 `gpt-realtime-2.1` 图片理解真机验收，未达到本阶段退出条件。

范围：

- 用户在 Talk 中用 `Control + Command` 主动框选一次屏幕区域，默认不持续监控。
- 截图按需压缩，不做无必要的重复上传。
- Realtime 会话接收图片上下文。
- 单纯添加图片不创建模型回复；用户继续说话后，模型才结合最近一次选区响应。
- 同一 Talk 只保留最近一次选区，再次框选时删除旧图片上下文。
- 以浮层、箭头、框选或文字提示给出指导。
- 设置页可查看屏幕录制权限并跳转系统设置，由用户撤销权限。

退出条件：

- 未触发时没有屏幕捕获行为。
- 用户可以看到当前请求是否包含截图。
- 标注层不会遮挡关键输入内容，也可以一键关闭。
- 屏幕权限拒绝时，Talk 和 Dictate 仍然可用。

### Phase 4：受控 Agent

目标：让 Friday 在明确授权下执行有限的多步骤任务。

当前状态：已完成 Qwen Audio Agent `v1.2.0` 的固定提交源码复核、Friday 目标技术架构、第一段受控 Mock Agent 主干和第一条可撤销本地 Action。Realtime Talk 可以把明确写入意图转换为 ActionProposal，本机解析用户说出的应用名、复验输入框并返回 ActionReceipt；同时仍可创建、确认或丢弃 `WorkDraft`，只有同一源 Turn 的最终用户转写和独立确认 Turn 都通过本地校验后，才会幂等创建 `mock_read_only` Work。正式 Work 可查询、取消并异步完成，对话不会被后台执行阻塞，完成结果会等待用户空闲后播报，被打断时重新排队。

这仍不是完整的多步骤 Agent：真实 Talk 的最终 ASR 已在开发验证版启用，但只在当前会话内用于来源、实时字幕和确认校验，尚未完成真机延迟与可靠性验收；Work objective 仍标记为 `model_derived`，Work 只存在内存，服务重启即丢失。当前唯一真实执行能力是无需确认、可用 `Command-Z` 撤销的输入框写入；没有真实 Agent Adapter、高风险权限确认、发送/提交等外部动作、持久化 Delivery 或任务管理界面。Mock Work 结果必须明确说明没有访问或修改任何外部内容。

长期架构约束如下；它们不再全部作为首个 Computer Use 垂直闭环的前置条件：

- Dictate、Conversation 和 Work 保持独立生命周期；Dictate 不经过重型 Agent，Conversation 不拥有后台执行循环。
- 原生 `ContextSnapshot` 区分可上传描述和只能留在客户端内存的 AX 目标句柄。
- Conversation History、长期 Memory 和 Work History 分开存储；当前用户原话优先于摘要和旧记忆。
- Talk 必须先取得可靠 final ASR，才能把用户原话写入 Conversation History 或生成 Memory 候选；文字任务和首个 Computer Use 验证不依赖这条链路。
- Context Assembler 按预算选择当前请求需要的最小数据，不把完整历史和全部记忆注入每次 Prompt。
- 活跃 Work 的进程所有权和退出语义明确：退出时选择继续后台运行或确认停止。
- 多步骤任务统一进入可查询、可取消和可去重的 Work 状态机；首个垂直闭环可使用内存 Store，跨重启前必须持久化。
- Agent 只能提出结构化 `ActionProposal`，本地 `ActionExecutor` 才能执行 macOS 动作。
- 执行路径优先官方 API、Chrome DOM 和 Accessibility，视觉坐标 Computer Use 只作受控兜底。
- 外部副作用的 Permission 必须绑定 owner、Work 和 Action，至少支持单次允许、会话允许和拒绝；首个低风险本地任务不因此增加确认。
- 模型生成、动作完成和结果交付分别记录，不用 `response.done` 冒充用户已经收到结果。

范围：

- 工具调用协议和本地动作执行器分离。
- 每个动作声明目标、风险和是否需要确认。
- 支持浏览器和少数高价值应用的最小适配器。
- 外部发送、删除、购买、提交表单等操作默认需要确认。
- 失败时停止在可恢复状态，并告诉用户下一步。

退出条件：

- 所有外部副作用都能在执行前展示并确认。
- Agent 可以暂停、取消和查看执行记录。
- 工具错误、权限错误和模型不确定都不会继续盲操作。
- 至少有一条端到端任务在真实 Mac 上稳定完成。

### Phase 5：公开 Beta 与分发

目标：让陌生用户能安全安装、理解权限并持续使用。

范围：

- 首次启动引导和权限说明。
- 账号、用量、限额和成本控制。
- 崩溃和错误诊断，默认不采集用户内容。
- Developer ID 签名、公证和 DMG 分发。
- 隐私政策、支持入口和数据删除流程。

退出条件：

- 新用户能在没有人工介入的情况下完成安装和权限配置。
- 能撤销权限、删除本地数据和注销服务。
- 公开版本有可追踪的版本号、构建号和回滚方案。

## 6. 用户故事与验收条件

### User Story US-001: 把测试文本放入原输入框

- **Summary：** 在不打开 Friday 窗口的情况下把整理后的文本放入当前输入框。

#### Use Case:

- **As a：** 正在使用 Mac 写消息的用户
- **I want to：** 让 Friday 找到当前获得焦点的输入框并插入文本
- **so that：** 我不需要在应用窗口和 AI 窗口之间来回复制粘贴

#### Acceptance Criteria:

- **Scenario：** Friday 保留触发前的输入目标
- **Given：** 我已在 TextEdit 中聚焦一个可写文本区域
- **and Given：** Friday 已记录该文本区域作为本次请求的目标
- **When：** 我在不重新点击该文本区域的情况下触发测试文本插入
- **Then：** 测试文本只出现在触发前记录的文本区域

### User Story US-002: 口述后生成适合场景的文本

- **Summary：** 把口语化内容改写成适合当前应用的文本。

#### Use Case:

- **As a：** 经常写邮件和工作消息的用户
- **I want to：** 用自然语言说明目的、语气和关键信息
- **so that：** 我可以直接发送或继续编辑，而不必先手动整理

#### Acceptance Criteria:

- **Scenario：** 用户口述一段邮件更新
- **Given：** 当前输入框是邮件正文，用户已授权麦克风
- **When：** 用户结束一轮语音输入
- **Then：** Friday 输出一段包含全部关键信息且符合用户指定语气的邮件正文

- **Scenario：** 口述内容是问题或未说完的句子
- **Given：** 用户口述“Hey, just wanted to confirm”后结束录音

- **Then：** 输出采用周四、保留“可能”和未确定含义、删除无意义停顿，并且不添加原语音中不存在的事实

### User Story US-012: 看见文本处理状态与最终结果

- **Summary：** 在模型处理期间看见明确状态，并且只展示通过校验的最终文本。

#### Use Case:

- **As a：** 正在用 Friday 口述输入的用户
- **I want to：** 看见录音、整理状态和最终结果
- **so that：** 我可以确认 Friday 正在工作，同时不会看到或写入未经校验的模型补写

#### Acceptance Criteria:

- **Scenario：** Realtime 模型返回增量文本并最终成功写回
- **Given：** 用户已结束一轮录音
- **When：** Realtime 返回文本增量和完成事件
- **Then：** 浮层在增量阶段只显示 Thinking 状态；最终文本通过听写输出校验后，Friday 才自动写回锁定目标，并在写回失败时保留可复制结果

### User Story US-013: 从展开灵动岛了解 Friday 状态

- **Summary：** 在展开灵动岛查看即时状态，并按需进入可关闭、可重开的原生主工作台。

#### Use Case:

- **As a：** 第一次使用 Friday 进行口述输入的 Mac 用户
- **I want to：** 从常驻灵动岛快速确认 Friday 是否可用，并从灵动岛或 Dock 进入完整主工作台
- **so that：** 我可以在轻量入口和完整管理界面之间切换，而不会因关窗中断后台语音能力

#### Acceptance Criteria:

- **Scenario：** 用户打开已具备必要权限的 Friday 面板
- **Given：** Friday 已正常启动并等待语音输入
- **and Given：** Mock Provider 仍可供开发测试使用
- **When：** 用户点击 Friday 的紧凑灵动岛
- **Then：** 约 `520 x 300` 的展开主页以中文展示当前状态、转写、语音 Agent、框选、最近一次结果和用量监控；权限恢复、服务详情和退出命令通过岛内设置页提供，且不展示模式选择、Provider、Mock 文本、最近目标、Token 密钥或内部错误堆栈

- **Scenario：** 在主页与设置之间切换
- **Given：** Friday 的展开主页已经显示
- **When：** 用户点击设置图标，再点击返回按钮
- **Then：** 同一个原生玻璃窗口从约 `520 x 300` 形变为约 `400 x 480` 的纵向菜单并恢复主页尺寸；窗口顶部中心始终固定，左右边缘和底边连续变化，不弹出第二个窗口，也不发生位置跳动

- **Scenario：** 从设置形态直接收起
- **Given：** Friday 正在显示纵向设置菜单
- **When：** 用户点击收起、按下 `Esc` 或点击窗口外部，然后再次展开灵动岛

- **Scenario：** 从灵动岛打开主工作台
- **Given：** Friday 正在显示灵动岛展开主页
- **When：** 用户点击设置图标左侧的展开按钮
- **Then：** 灵动岛收起并显示唯一的原生主工作台；工作台使用 Flow 风格的全高浅色侧边栏、Iconsax 波形品牌图标和白色圆角内容画布，不创建第二个窗口，也不启动麦克风或模型会话

- **Scenario：** 关闭主工作台后继续运行
- **Given：** Friday 已显示 Dock 图标、主工作台和常驻灵动岛
- **When：** 用户点击主窗口关闭按钮

### User Story US-014: 只在完整链路可用时显示就绪

- **Summary：** 在开始录音前准确知道 Friday 是否可以完成本轮输入。

#### Use Case:

- **As a：** 依赖 Friday 完成跨应用口述输入的用户
- **I want to：** 只在权限、快捷键和语音服务均可用时看到“已就绪”
- **so that：** 我不会录完一段内容后才发现本轮无法处理

#### Acceptance Criteria:

- **Scenario：** 本地语音服务在 Friday 运行期间停止
- **Given：** Friday 已获得辅助功能和麦克风权限，且快捷键注册成功
- **and Given：** Friday 当前使用 Live 模式
- **When：** 用户刷新状态或尝试开始一轮输入
- **Then：** Friday 在录音前显示语音服务不可用，并在服务恢复后无需重启 App 即可恢复就绪

### User Story US-015: 处理失败后无需重新口述

- **Summary：** 临时服务错误不会让用户失去已经完成的口述。

#### Use Case:

- **As a：** 已经完成一段工作内容口述的用户
- **I want to：** 在模型处理失败后直接重试
- **so that：** 我不需要因为网络或服务波动重新说一遍

#### Acceptance Criteria:

- **Scenario：** 录音完成后 Realtime 处理失败
- **Given：** Friday 已在内存中保留本轮音频和原输入目标
- **When：** 用户点击重试
- **Then：** Friday 使用同一段内存音频重新处理，并在成功或取消后清除本轮音频

### User Story US-016: 写入失败后恢复结果

- **Summary：** 目标输入框异常时仍能保住已经生成的文字。

#### Use Case:

- **As a：** 已经等待 Friday 完成文字整理的用户
- **I want to：** 在写入失败后重新写入或复制结果

#### Acceptance Criteria:

- **Scenario：** Friday 已生成文字但原输入目标暂时无法写入
- **Given：** Friday 保留最终文本和原输入目标
- **When：** 用户点击重试写入
- **Then：** Friday 只重新执行写入而不再次调用模型，并且不会在无法确认写入时显示成功

## 7. 明确不做的事情

- Phase 1 不做持续屏幕监控。
- Phase 1 不做任意鼠标坐标猜测和无确认点击。
- Phase 2 不把长期 OpenAI API Key 放进客户端。
- Phase 1 不对完全自绘且不向 macOS Accessibility 暴露编辑语义的控件猜测写入；这类场景必须降级为展示和复制结果。
- 没有稳定的 Mock 模式前，不把 API 调用写进 UI 预览逻辑。
- 没有权限、撤销和确认机制前，不开放自动发送、删除、购买或提交。

## 8. 衡量指标

第一阶段只关注产品是否可用，不先追求增长：

- 从快捷键到文本插入的成功率。
- 找不到目标输入框的误写率，目标为 0。
- 用户从口述结束到看到结果的延迟。
- 用户撤销或重写的比例。
- 权限拒绝后仍能继续使用的能力比例。
- 每次有效输入的 API 成本。

## 9. 当前未决问题

这些问题需要产品负责人确认后再进入对应阶段：

1. 首发是否只支持 macOS 14.0+，还是提高到 14.2+。
2. 首个 Realtime Provider 使用官方 OpenAI，还是先接入其他可用供应商。
3. 默认采用按住说话还是按一下开始、再按一下结束。
4. 改写结果默认直接插入，还是始终先显示可撤销预览。
5. 首个公开测试用户是创作者、开发者，还是普通办公用户。
6. Conversation History 的默认保留期限，以及是否允许用户选择“仅本次会话”。
7. proposed Memory 采用即时确认、集中整理，还是两者并存的产品交互。
8. Talk final ASR 首选额外计费的官方输入转写、本机 ASR，还是其他可替换 Provider。
