# Friday 工程问题与复盘

> 版本：0.1 · 建立日期：2026-08-03

这份文档记录 Friday 开发中值得复用的问题排查过程和工程经验，服务于后续维护、作品介绍和面试复盘。它不是开发流水账，也不替代 Issue、PR、架构文档或产品路线图。

## 1. 记录目的

每条记录需要让不了解当时上下文的人回答以下问题：

1. 用户实际遇到了什么，影响是什么。
2. 当时掌握了哪些证据，哪些只是猜测。
3. 排查过哪些方向，为什么排除或保留。
4. 根因最终是什么，修复为什么有效。
5. 如何验证，哪些部分仍未验证。
6. 这次经历对后续架构、测试或产品设计有什么可复用价值。

## 2. 什么时候必须记录

出现以下任一情况时，在排查开始时建立记录，并随着证据更新：

- 问题反复出现，或一次排查无法直接定位。
- 涉及多个模块、异步状态、并发、音频、网络、系统权限或外部 Provider。
- 修复过程中出现过有迷惑性的现象、错误假设或无效方案。
- 涉及隐私、API 费用、数据丢失、不可逆操作或安全边界。
- 问题会影响核心用户流程、架构设计或发布判断。
- 解决方案具有作品介绍、面试讲解或后续复用价值。

错别字、纯视觉微调、明确的一行配置修复和没有分析价值的机械维护不单独记录。若小问题暴露了更深层的流程或架构缺陷，则记录深层问题。

## 3. 记录时机与状态

不要等问题解决后凭记忆补写。记录跟随排查过程更新：

```text
发现问题
→ 建立“调查中”条目，写入现象和第一手证据
→ 记录假设、实验与结果
→ 找到根因后更新为“已定位”
→ 修复并验证后更新为“已解决”
→ 真机或生产证据不足时保持“待验证”
```

允许的状态：

| 状态 | 含义 |
| --- | --- |
| `调查中` | 已确认现象，但根因尚未确定。 |
| `已定位` | 根因已有充分证据，修复或验证尚未完成。 |
| `待验证` | 已实现修复，仍缺少必要的真机、权限或真实网络验证。 |
| `已解决` | 修复和约定的验证均已完成。 |
| `暂缓` | 影响和风险已知，当前明确决定不处理，并写明恢复条件。 |

只有证据支持时才能写“根因”和“已解决”。排查中的判断写在“假设与实验”，不能事后删除错误尝试；应简要说明它为什么不成立。

## 4. 与其他文档的关系

| 载体 | 负责回答的问题 |
| --- | --- |
| GitHub Issue | 为什么要做、范围是什么、怎样验收。 |
| 分支与 PR | 具体改了什么、如何审查和回滚。 |
| 产品路线图决策记录 | 为什么选择某个产品或架构方向。 |
| 本文档 | 难点如何出现、如何定位、为何这样修复、学到了什么。 |
| 本地诊断日志 | 某次运行实际发生了哪些事件，作为复盘证据之一。 |

一条复盘可以关联多个 Issue 或 PR，但不复制完整代码差异。长期结论如果改变系统设计，应同步到架构文档；用户行为或阶段门槛变化，应同步到产品路线图。

## 5. 隐私与证据边界

- 不记录 API Key、Token、Authorization header、密码或账号凭证。
- 不粘贴原始音频、完整对话、完整转写、完整截图或用户私有文件内容。
- 日志只摘录定位问题所需的无内容事件、时间、状态、错误码和脱敏字段。
- 外部资料注明来源、访问日期和版本；会变化的信息不写成永久事实。
- 命令输出只保留关键证据，不把大段构建日志复制进文档。
- 无法复现时写明观察范围，不为了让记录完整而虚构根因。

## 6. 条目模板

新增记录时复制下面模板。编号格式为 `FRD-YYYYMMDD-NNN`，同一天从 `001` 递增。

```markdown
## FRD-YYYYMMDD-NNN：问题标题

- 状态：调查中 / 已定位 / 待验证 / 已解决 / 暂缓
- 首次发现：YYYY-MM-DD
- 最近更新：YYYY-MM-DD
- 影响范围：Dictate / Talk / Agent / Platform / Backend / 工程流程
- 关联：Issue、PR、Commit、日志或文档；没有则写“待创建”或“不适用”

### 用户现象与影响

描述用户能观察到的实际行为、期望行为和影响，不先写技术结论。

### 环境与复现

记录系统、构建、触发条件、复现频率和最小步骤。无法稳定复现时明确说明。

### 证据

按时间列出日志事件、命令结果、源码位置或真机观察，并区分自动检查与人工验收。

### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 示例假设 | 执行的最小实验 | 观察结果 | 保留 / 排除 / 证据不足 |

### 根因

只有在证据充分后填写。调查中写“尚未确定”。

### 解决方案

说明修复策略、关键取舍、为什么选择它，以及明确没有做什么。

### 验证结果

列出自动测试、构建、真实 Mac 验收和仍未覆盖的场景。

### 经验与后续

总结可以迁移到其他模块或面试讲解的经验，并列出需要同步到架构、测试或产品文档的动作。
```

## 7. 问题记录

### FRD-20260803-001：本地语音服务监听端口但健康检查超时

- 状态：`已解决`
- 首次发现：2026-08-03
- 最近更新：2026-08-03
- 影响范围：Backend、本地开发流程
- 关联：`Backend/service-manager.mjs`、`Backend/server.mjs`

#### 用户现象与影响

本地服务进程显示仍在运行且 `127.0.0.1:8787` 有监听，但健康检查无法得到响应。Friday 因此不能仅凭端口监听判断语音服务已经可用，可能表现为“进程存在但服务未连接”。

#### 环境与复现

- macOS 本地开发环境。
- 长时间运行的 Node 进程：`Backend/server.mjs`。
- 对 `http://127.0.0.1:8787/health` 发起三秒超时的只读请求。

修改前在重新启动的服务上可以稳定复现：`/health` 会等待 OpenAI 请求，网络不可达时五秒内没有响应。

#### 证据

- `lsof -nP -iTCP:8787 -sTCP:LISTEN` 显示 Node 进程正在监听 `127.0.0.1:8787`。
- `curl --max-time 3 http://127.0.0.1:8787/health` 在三秒内收到 `0` 字节，结果为 `HTTP 000`。
- 隔离的后端 Mock Work API 测试使用随机本地端口可以完成提交、去重、查询和取消。这只能证明对应测试路径可运行，不能证明长期运行的 `8787` 进程健康。
- 源码确认旧 `/health` 路由在发送任何 HTTP 响应前执行 `await checkUpstreamReadiness()`，而上游检查自身最长等待五秒。
- 本次检查没有创建 Realtime 凭证，也没有触发付费模型响应。

#### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 服务根本没有启动 | 检查 TCP 监听和进程 | 端口和进程均存在 | 排除 |
| 后端 Work 路由代码整体无法运行 | 运行隔离的 Mock Work API 测试 | 测试通过 | 对测试覆盖路径排除，不能代表常驻进程 |
| 常驻进程卡住、旧代码未重启或事件循环被阻塞 | 受控重启后再次请求旧 `/health` | 新进程仍因上游请求等待而超时 | 排除“只由旧进程导致” |
| 本地健康端点错误地同步等待 OpenAI | 阅读路由并在网络不可达时分别观察 TCP、HTTP 和上游请求 | 端口已监听，但 `/health` 在上游检查结束前不发送响应 | 确认 |

#### 根因

本地存活与 OpenAI 模型就绪被合并到同一个 `/health` 路由。路由在返回本地状态前同步等待带五秒超时的模型元数据请求；Friday 客户端和管理脚本自身又使用更短超时，因此会先中止并把“上游暂不可达”表现成“本地服务未连接”。

#### 解决方案

- `/health` 只读取本地诊断状态，返回 `upstream_status: "unchecked"`，不访问 OpenAI。
- 新增 `/ready`，只在有边界超时的模型元数据检查通过后返回 ready。
- Friday 客户端改用 `/ready`，因此不会把本地进程存活误报为 Live 可用。
- `npm start` 用 `/health` 判断服务是否已经监听；`npm run status` 和 `doctor` 分开报告本地与模型状态。
- 上游就绪默认三秒超时；成功与失败结果继续使用短期缓存，检查不会创建 Realtime 凭证或模型回复。

#### 验证结果

- 后端假上游测试 `10/10` 通过，包含上游延迟时 `/health` 仍快速返回、`/ready` 有界失败、状态命令分层输出和错误脱敏。
- Swift 客户端定向测试通过，确认模型就绪客户端使用 `/ready`。
- 真实本地服务中，`/health` 约 `6ms` 返回 HTTP 200；当前 OpenAI 网络不可达时，`/ready` 约 `3.0s` 返回 HTTP 503 和脱敏恢复提示。
- `npm run status` 同时输出“Local service: listening”和“OpenAI models: unavailable”，不再混淆两层状态。
- 未创建 Realtime 凭证，未发送音频，也未触发付费模型响应。
- 当前网络路由仍未恢复，因此没有在本轮验证 `/ready` 的真实 HTTP 200；成功路径已由本地假 OpenAI 上游覆盖。

#### 经验与后续

- 进程存在不是服务健康证据，交付检查必须使用有超时的应用层健康请求。
- Liveness 和 Readiness 是不同契约：前者回答进程能否服务，后者回答关键外部依赖能否完成产品请求。
- 客户端超时必须大于服务端上游超时，否则服务端准备好的错误信息会被客户端提前丢弃。
- 自动交付报告继续分开说明“本地服务已监听”和“OpenAI 模型已就绪”，任何一层都不能代替另一层。
