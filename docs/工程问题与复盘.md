# Friday 工程问题与复盘

> 版本：0.1 · 建立日期：2026-08-03

这份文档记录 Friday 开发中值得复用的问题排查过程和工程经验，服务于后续维护、作品介绍和面试复盘。它不是开发流水账，也不替代 Issue、PR、架构文档或产品路线图。

## 1. 记录目的

每条记录需要让不了解当时上下文的人回答以下问题：

1. 用户实际遇到了什么，影响是什么。
2. 当时掌握了哪些证据，哪些只是猜测。
3. 排查过哪些方向，为什么排除或保留。
4. 根因最终是什么，修复为什么有效。
5. 如何验证，哪些部分仍未验证。
6. 这次经历对后续架构、测试或产品设计有什么可复用价值。

## 2. 什么时候必须记录

出现以下任一情况时，在排查开始时建立记录，并随着证据更新：

- 问题反复出现，或一次排查无法直接定位。
- 涉及多个模块、异步状态、并发、音频、网络、系统权限或外部 Provider。
- 修复过程中出现过有迷惑性的现象、错误假设或无效方案。
- 涉及隐私、API 费用、数据丢失、不可逆操作或安全边界。
- 问题会影响核心用户流程、架构设计或发布判断。
- 解决方案具有作品介绍、面试讲解或后续复用价值。

错别字、纯视觉微调、明确的一行配置修复和没有分析价值的机械维护不单独记录。若小问题暴露了更深层的流程或架构缺陷，则记录深层问题。

## 3. 记录时机与状态

不要等问题解决后凭记忆补写。记录跟随排查过程更新：

```text
发现问题
→ 建立“调查中”条目，写入现象和第一手证据
→ 记录假设、实验与结果
→ 找到根因后更新为“已定位”
→ 修复并验证后更新为“已解决”
→ 真机或生产证据不足时保持“待验证”
```

允许的状态：

| 状态 | 含义 |
| --- | --- |
| `调查中` | 已确认现象，但根因尚未确定。 |
| `已定位` | 根因已有充分证据，修复或验证尚未完成。 |
| `待验证` | 已实现修复，仍缺少必要的真机、权限或真实网络验证。 |
| `已解决` | 修复和约定的验证均已完成。 |
| `暂缓` | 影响和风险已知，当前明确决定不处理，并写明恢复条件。 |

只有证据支持时才能写“根因”和“已解决”。排查中的判断写在“假设与实验”，不能事后删除错误尝试；应简要说明它为什么不成立。

## 4. 与其他文档的关系

| 载体 | 负责回答的问题 |
| --- | --- |
| GitHub Issue | 为什么要做、范围是什么、怎样验收。 |
| 分支与 PR | 具体改了什么、如何审查和回滚。 |
| 产品路线图决策记录 | 为什么选择某个产品或架构方向。 |
| 本文档 | 难点如何出现、如何定位、为何这样修复、学到了什么。 |
| 本地诊断日志 | 某次运行实际发生了哪些事件，作为复盘证据之一。 |

一条复盘可以关联多个 Issue 或 PR，但不复制完整代码差异。长期结论如果改变系统设计，应同步到架构文档；用户行为或阶段门槛变化，应同步到产品路线图。

## 5. 隐私与证据边界

- 不记录 API Key、Token、Authorization header、密码或账号凭证。
- 不粘贴原始音频、完整对话、完整转写、完整截图或用户私有文件内容。
- 日志只摘录定位问题所需的无内容事件、时间、状态、错误码和脱敏字段。
- 外部资料注明来源、访问日期和版本；会变化的信息不写成永久事实。
- 命令输出只保留关键证据，不把大段构建日志复制进文档。
- 无法复现时写明观察范围，不为了让记录完整而虚构根因。

### FRD-20260803-001：本地语音服务监听端口但健康检查超时

- 状态：`已解决`
- 首次发现：2026-08-03
- 最近更新：2026-08-03
- 影响范围：Backend、本地开发流程
- 关联：`Backend/service-manager.mjs`、`Backend/server.mjs`

#### 用户现象与影响

本地服务进程显示仍在运行且 `127.0.0.1:8787` 有监听，但健康检查无法得到响应。Friday 因此不能仅凭端口监听判断语音服务已经可用，可能表现为“进程存在但服务未连接”。

#### 环境与复现

- macOS 本地开发环境。
- 长时间运行的 Node 进程：`Backend/server.mjs`。
- 对 `http://127.0.0.1:8787/health` 发起三秒超时的只读请求。

修改前在重新启动的服务上可以稳定复现：`/health` 会等待 OpenAI 请求，网络不可达时五秒内没有响应。

#### 证据

- `lsof -nP -iTCP:8787 -sTCP:LISTEN` 显示 Node 进程正在监听 `127.0.0.1:8787`。
- `curl --max-time 3 http://127.0.0.1:8787/health` 在三秒内收到 `0` 字节，结果为 `HTTP 000`。
- 隔离的后端 Mock Work API 测试使用随机本地端口可以完成提交、去重、查询和取消。这只能证明对应测试路径可运行，不能证明长期运行的 `8787` 进程健康。
- 源码确认旧 `/health` 路由在发送任何 HTTP 响应前执行 `await checkUpstreamReadiness()`，而上游检查自身最长等待五秒。
- 本次检查没有创建 Realtime 凭证，也没有触发付费模型响应。

#### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 服务根本没有启动 | 检查 TCP 监听和进程 | 端口和进程均存在 | 排除 |
| 后端 Work 路由代码整体无法运行 | 运行隔离的 Mock Work API 测试 | 测试通过 | 对测试覆盖路径排除，不能代表常驻进程 |
| 常驻进程卡住、旧代码未重启或事件循环被阻塞 | 受控重启后再次请求旧 `/health` | 新进程仍因上游请求等待而超时 | 排除“只由旧进程导致” |
| 本地健康端点错误地同步等待 OpenAI | 阅读路由并在网络不可达时分别观察 TCP、HTTP 和上游请求 | 端口已监听，但 `/health` 在上游检查结束前不发送响应 | 确认 |

#### 根因

本地存活与 OpenAI 模型就绪被合并到同一个 `/health` 路由。路由在返回本地状态前同步等待带五秒超时的模型元数据请求；Friday 客户端和管理脚本自身又使用更短超时，因此会先中止并把“上游暂不可达”表现成“本地服务未连接”。

#### 解决方案

- `/health` 只读取本地诊断状态，返回 `upstream_status: "unchecked"`，不访问 OpenAI。
- 新增 `/ready`，只在有边界超时的模型元数据检查通过后返回 ready。
- Friday 客户端改用 `/ready`，因此不会把本地进程存活误报为 Live 可用。
- `npm start` 用 `/health` 判断服务是否已经监听；`npm run status` 和 `doctor` 分开报告本地与模型状态。
- 上游就绪默认三秒超时；成功与失败结果继续使用短期缓存，检查不会创建 Realtime 凭证或模型回复。

#### 验证结果

- 后端假上游测试 `10/10` 通过，包含上游延迟时 `/health` 仍快速返回、`/ready` 有界失败、状态命令分层输出和错误脱敏。
- Swift 客户端定向测试通过，确认模型就绪客户端使用 `/ready`。
- 真实本地服务中，`/health` 约 `6ms` 返回 HTTP 200；当前 OpenAI 网络不可达时，`/ready` 约 `3.0s` 返回 HTTP 503 和脱敏恢复提示。
- `npm run status` 同时输出“Local service: listening”和“OpenAI models: unavailable”，不再混淆两层状态。
- 未创建 Realtime 凭证，未发送音频，也未触发付费模型响应。
- 当前网络路由仍未恢复，因此没有在本轮验证 `/ready` 的真实 HTTP 200；成功路径已由本地假 OpenAI 上游覆盖。

#### 经验与后续

- 进程存在不是服务健康证据，交付检查必须使用有超时的应用层健康请求。
- Liveness 和 Readiness 是不同契约：前者回答进程能否服务，后者回答关键外部依赖能否完成产品请求。
- 客户端超时必须大于服务端上游超时，否则服务端准备好的错误信息会被客户端提前丢弃。
- 自动交付报告继续分开说明“本地服务已监听”和“OpenAI 模型已就绪”，任何一层都不能代替另一层。

### FRD-20260803-002：Talk 音频所有权与 Provider 生命周期耦合

- 状态：`已解决`
- 首次发现：2026-08-03
- 最近更新：2026-08-03
- 影响范围：Talk、Platform、Provider、架构迁移
- 关联：[Issue #8](https://github.com/jason2kkk/Friday/issues/8)、[Issue #6](https://github.com/jason2kkk/Friday/issues/6)

#### 用户现象与影响

当前直接 Realtime Talk 可以运行，但端点、插话和误插话恢复仍需要持续调校。项目希望参考 LiveKit 的 Session Runtime 验证这些能力，同时保留 Friday 原生灵动岛、屏幕框选、Accessibility 和 Work 安全边界。

现有代码让 `ConversationCoordinator` 分别启动本地音频服务和模型 Provider，隐含“Friday 永远自己采集和播放 PCM”。如果直接加入由 SDK 管理麦克风、播放与 AEC 的候选 Runtime，可能产生双重采集、双重回声消除或设备争用，无法进行可信对比。

#### 环境与复现

- 当前分支基于 Phase 3 Alpha 基线。
- 修改前 `ConversationCoordinator.startConversation` 先调用 `audioService.start()`，再调用 `conversationProvider.connect()`。
- 修改前 `finishConversation`、`stop` 分别调用 `conversationProvider.disconnect()` 和 `audioService.stop()`；修改后 Coordinator 只调用 `conversationRuntime.start/stop`。
- LiveKit 仍是候选方案；当前没有引入 SDK、Room、Token 或真实音频测试。

#### 证据

- 当前 `ConversationProviding` 以 `append(AudioChunk)` 和 `assistantAudio(Data)` 表达 App 管理的 PCM 边界。
- 当前 `ConversationAudioServicing` 由 `ConversationAudioService` 实现，并直接拥有 VoiceProcessingIO 或 AVAudioEngine。
- 《LiveKit Talk 技术验证计划》要求第一轮候选验证由 LiveKit Swift SDK 独占设备音频，不能与上述服务并行。
- 本次调查尚未创建 Realtime 或 LiveKit 凭证，也没有触发付费模型响应。

#### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 只增加另一个 `ConversationProviding` 就能安全接入 LiveKit | 对照现有启动顺序和 PCM 事件契约 | Provider 无法阻止 Coordinator 另行启动本地设备音频 | 排除 |
| 让 Coordinator 根据 Provider 类型写条件分支即可 | 评估依赖方向和回滚边界 | Feature 层会知道供应商类型，后续每个 Runtime 都继续扩张条件分支 | 不采用 |
| 抽出同时拥有 Provider、音频端口和启停顺序的 Runtime Session | 用现有 Realtime 包装器和假 LiveKit Transport 做零费用契约测试 | 8 条聚焦测试覆盖两种所有权、启停顺序、失败清理、录制禁用、事件映射与 RPC | 采纳 |

#### 根因

本条没有证明现有语音体验故障由该耦合直接导致；已确认的根因是架构层把会话启停放在 Coordinator，并把物理音频所有权隐式固定为 Friday 本地实现。单独替换 Provider 无法阻止另一套 SDK 再启动设备音频，因此缺少可以原子装配和启停一套 Talk Runtime 的中立边界。

#### 解决方案

已引入 `ConversationRuntimeSession`：由它原子提供 Provider、音频端口、Runtime 描述和统一启停。`DirectRealtimeConversationRuntimeSession` 保持“先本地音频、后 Realtime Provider”的现有顺序，并在失败或取消时统一清理；App 组合根仍只选择这条产品路径。

LiveKit Stage 0 使用假 `LiveKitConversationTransporting`，同一个 Runtime 同时实现 Provider 与音频端口，并以配置校验保证 Runtime 音频独占和 `recordSession=false`。Provider 自管播放通过中立事件进入 Friday 的 Turn/Playback 状态，但不把 PCM 再交给 Friday 播放。ActionProposal/Receipt 只通过带版本和大小上限的 RPC 数据契约传输，不执行动作。

本轮不引入 LiveKit SDK、不替换当前 Talk、不创建真实凭证，也不把 Action 执行权限交给远端 Runtime。

#### 验证结果

8 条 `ConversationRuntimeTests` 已通过，覆盖 Direct Realtime 启停顺序与 Provider 失败清理、LiveKit 禁止录制、单一 Transport 音频所有权、Transport 启动失败清理、Room Token 日志脱敏、ActionProposal/Receipt RPC 往返，以及非法 ID、版本、方法和消息大小拒绝。无签名 Debug 构建、`Info.plist`、工程文件和差异检查通过。

这些自动证据没有访问麦克风、网络、LiveKit Cloud 或 OpenAI，也没有创建凭证和付费响应。尚未引入 LiveKit SDK、真实 Room 或 Agent 进程；真实 `gpt-realtime-2.1` 兼容性、AEC、Adaptive Interruption、延迟、费用和中文对话体验仍未验证，因此条目保持“待验证”。

#### 经验与后续

- 可替换 Provider 不等于可替换 Runtime；谁拥有设备音频、端点和播放回执必须成为显式架构契约。
- 供应商选择应停留在组合根，Feature Coordinator 只依赖中立 Runtime，不能用 Provider 类型判断行为。
- 零费用 Stage 0 只能证明边界可接，不能证明 LiveKit 或 `gpt-realtime-2.1` 的真实兼容性和体验收益。

### FRD-20260803-004：Talk 本地停说后一直停留在收听状态

- 状态：`代码已修复，待真机验收`
- 首次发现：2026-08-03
- 最近更新：2026-08-03
- 影响范围：Talk、Platform、Realtime Provider、用户 Turn 状态
- 关联：[Issue #10](https://github.com/jason2kkk/Friday/issues/10)、`Friday/Platform/ConversationAudioService.swift`、`Friday/Features/ConversationCoordinator.swift`

#### 用户现象与影响

用户在 Talk 中说了多段话并停下，灵动岛持续显示收听状态，超过一分钟仍没有回复，只能手动结束会话。这会让用户误以为网络或模型没有收到语音，实际回复请求根本没有被创建。

#### 环境与复现

- 真实 Mac、VoiceProcessingIO 全双工 AEC、蓝牙输入/输出设备。
- Talk 使用 `gpt-realtime-2.1`、`near_field` 和 high-eagerness semantic VAD，服务端自动回复关闭，由客户端在端点后创建回复。
- 诊断会话：`2cd3ada7-4dbc-4b81-ba3c-a77bf4930952`，2026-08-03 21:16:19 至 21:17:38。
- 用户说话并停下后可以稳定观察到本地释放事件，但没有 Provider 停说事件。

#### 证据

- 会话启动、本地音频、Realtime WebSocket 和开场问候全部成功；开场回复从创建到首段音频约 596ms，排除“模型或网络完全不可用”。
- 21:16:32.685 本地输入门确认语音，21:16:32.978 Provider 产生 `speech_started`。
- 本地分别在 21:16:33.245、21:16:35.286 和 21:16:52.306 产生 `speech_released`，Provider 始终没有产生 `speech_stopped`。
- 日志中没有用户回复的 `response.request_scheduled`、`response.requested` 或新的 `response.started`，也没有 Provider、WebSocket、token 或费用错误。
- `ConversationInputGate` 在约 550ms 静音后把 `speechIsActive` 设为 false；空闲分支在下一次语音重新确认前返回空数组，因此不会继续向 Realtime 提交端点静音。
- Coordinator 对本地 `speechReleased` 原先只写诊断，只有 Provider 的 `userSpeechStopped` 才会进入 450ms 续句窗口并创建回复。
- 2026-08-03 查询 OpenAI 官方 Realtime VAD 与 WebSocket 指南：VAD 开启时由服务端从流式 `input_audio_buffer.append` 产生 `speech_started` / `speech_stopped`；`input_audio_buffer.commit` 是关闭 VAD 时的路径。

#### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 网络或 API Key 失效导致没有回复 | 对照同会话开场回复、WebSocket 生命周期和错误事件 | 开场回复正常，连接保持约 75 秒且无失败事件 | 排除 |
| 模型已开始生成但回复被播放层丢失 | 查找用户 Turn 后的 Response、Assistant Item 和音频事件 | 用户 Turn 后没有创建 Response | 排除 |
| 本地输入门先停止上传，使 semantic VAD 缺少形成端点所需的连续静音 | 对齐本地 release、Provider stop 和音频门返回路径 | 多次本地 release 后均无 Provider stop；源码确认 release 后停止输出 | 确认 |
| 直接在 VAD 开启时手工 commit 可以安全兜底 | 查询官方 Realtime 文档 | 官方把 commit 明确放在 VAD 关闭流程；混用会引入竞态 | 不采用 |

#### 根因

Friday 同时使用本地声学输入门和 Realtime semantic VAD，但没有定义两者之间的端点交接。本地输入门只保留约 550ms 尾音，随后停止向网络发送任何帧；semantic VAD 已经打开用户 Turn，却没有获得足够连续静音来产生 `speech_stopped`。Coordinator 又只相信 Provider 端点，因此用户状态和回复调度会无限等待。

#### 解决方案

- 本地输入门释放已经确认的语音后，继续向 Realtime 提交最长四秒的零值 PCM，不上传房间背景声。
- 在静音尾期间重新确认有效语音时立即取消旧静音尾，并把最多约 450ms 预录真实语音继续交给同一会话。
- 四秒静音耗尽仍没有 Provider 端点时记录 `input_gate.endpoint_silence_exhausted`，结束卡住的 Talk 并提示用户重试；即使 Provider 连 `speech_started` 都没有产生，也不会无限等待。
- 保持 semantic VAD 开启，不发送手工 `input_audio_buffer.commit`，继续由 Provider 端点触发现有 450ms 续句窗口和单次 `response.create`。

#### 验证结果

- `TalkInteractionTests` 定向套件通过。
- 新测试覆盖：本地 release 后继续输出零值 PCM、四秒上限和耗尽事件、恢复语音取消静音尾并保留预录、Coordinator 在端点耗尽后退出 `user_speaking`。
- 自动测试没有访问麦克风、OpenAI 或真实网络，没有创建 Realtime 凭证和付费响应。
- 尚未用真实中文语音验证 `gpt-realtime-2.1` 返回 `speech_stopped` 的实际时机，因此状态保持“待真机验收”。

#### 经验与后续

- 本地 VAD 与云端 VAD 不能各自独立截断流；端点所有权和交接必须是 Runtime 契约的一部分。
- Mock 直接发出 `speech_stopped` 只能验证收到端点后的状态机，不能证明真实音频一定能产生端点。
- 音频交互测试至少要覆盖“最后一个真实语音帧之后发送了什么”，否则最基础的停说失败会被事件级单测掩盖。

### FRD-20260803-005：语音 Agent 重复填充话术且无法按应用名写入

- 状态：`代码已修复，待真机验收`
- 首次发现：2026-08-03
- 最近更新：2026-08-03
- 影响范围：Talk Prompt、Realtime 工具、应用意图、本地 Action、灵动岛准备态
- 关联：[Issue #4](https://github.com/jason2kkk/Friday/issues/4)

#### 用户现象与影响

Talk 听到用户后会重复需求、介绍能力或反复邀请用户继续说明；当用户明确要求把文字写入 Codex 输入框时，模型报告请求被拒绝并回到收听状态。用户停说后，声波还会先显示灰色再变为粉色，使正常推理等待看起来像一次多余状态切换。

#### 环境与复现

- 当前产品路径为 Direct Realtime Talk，默认模型 `gpt-realtime-2.1`。
- final input transcription 默认关闭，因此依赖用户原话核对的 Work 工具不会暴露。
- 本机 Codex 安装路径为 `/Applications/ChatGPT.app`，Bundle ID 为 `com.openai.codex`，系统显示名为 ChatGPT。
- 本轮自动验证只使用 Mock Provider 和本地假 OpenAI 上游，没有创建 Realtime 凭证或写入真实应用。

#### 证据

- 修改前 Talk 工具列表没有真实输入框写入工具；已有 `ActionProposal/ActionReceipt` 只定义数据契约，没有从 Realtime 工具事件到本地 Accessibility 的执行链。
- 修改前 Prompt 对普通回复允许一到三句，工具跟进上限为 80 token，普通 Talk 上限为 640 token，不能确定性阻止重复复述和能力介绍。
- 修改前 Assistant 准备阶段使用 `source: .idle`，而音频到达后切换到 `source: .assistant`，直接解释了灰色到粉色的视觉跳变。
- `NSWorkspace` 证据显示用户说的 Codex 与系统显示名 ChatGPT 不一致，仅比较显示名无法可靠解析目标应用。

#### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 只在 Prompt 中要求模型“识别 Codex”即可安全执行 | 对照本地运行应用和 Bundle ID | 模型名称不能证明目标进程身份，也不能验证输入框 | 排除 |
| 复用后台 Work 提交路径处理一次文字写入 | 对照生命周期与权限 | 可撤销即时写入不需要排队、持久化或二次确认，进入 Work 会不必要地阻塞交互 | 不采用 |
| Realtime 解释文字和应用意图，本机生成 ActionProposal 并执行 | 用 Codex 别名、通用应用、显式目标优先、失败与重复 Tool Call 测试 | 目标身份和执行证据都留在可信本地层，Talk 仍保持连接 | 采纳 |
| 灰色声波是模型或网络延迟造成 | 对照 Presentation 状态映射 | 准备态明确使用 idle source，音频态才使用 assistant source | 排除网络根因，修复状态映射 |

#### 根因

产品已经有“模型提出 Action、客户端凭回执确认执行”的目标架构，但实际 Talk 仍只接入 Mock Work 工具，缺少即时可撤销写入的 Tool Intent Bridge、本机应用身份解析和 ActionExecutor。与此同时，Prompt 与 token 上限偏宽，允许模型用重复复述和能力介绍填充回复；Presentation 又把同一个 Assistant 回合拆成两种颜色来源。

#### 解决方案

- 后端始终向 Talk 暴露 `write_focused_input(text, application?)`，而依赖 final ASR 的 Work 工具继续保持关闭。
- `ConversationActionBridge` 校验参数、生成 `reversibleLocalWrite` ActionProposal，并按 Tool Call ID 缓存输出，避免重复执行。
- `RunningApplicationResolver` 使用运行应用、显示名、Bundle ID 和有限别名解析用户原话；显式应用优先于 Talk 启动时锁定的目标，未知或歧义结果不回退。
- `FocusedInputActionExecutor` 只接受无需确认、可撤销的文字写入，复验目标后复用剪贴板粘贴路径，并返回 `succeeded/failed/unknown` ActionReceipt。
- 普通 Talk 输出上限降为 220 token，工具跟进降为 48 token；Prompt 禁止复述、能力介绍和工具前口播，写入成功后只说“写好了”。
- Assistant 准备态直接使用静止粉色声波，真实音频到达后只改变高度，不再经历灰色到粉色。

#### 验证结果

- 后端 10 条假上游测试通过，覆盖无 final ASR 时仍暴露可撤销写入、Work 工具保持隐藏和新 Prompt 版本。
- 7 条 Agent Action 聚焦测试通过，覆盖 Codex Bundle ID、通用运行应用、显式应用优先、会话目标兜底、未知应用、unknown 回执和重复 Tool Call 幂等。
- Coordinator 聚焦测试确认工具回执返回后 Talk 仍连接且可继续。
- 无签名 Debug 构建、`Info.plist`、工程文件和差异检查通过；未创建 Realtime 凭证或付费模型回复。
- 尚未用真实语音和真实 Accessibility 目标验收，因此状态保持“待真机验收”。

#### 经验与后续

- Qwen/LiveKit 值得参考的是职责分层与结构化回执，不是把其运行时或 SDK 直接并入 Friday；macOS 应用身份和输入目标必须由本机可信层负责。
- 模型可以解释“用户想操作哪个应用”，但不能证明“这个进程和控件就是安全目标”；语义意图与系统身份必须分开。
- 可撤销即时 Action 与后台 Work 是两条不同生命周期。只有复杂、异步、可查询的任务才应创建工单。
- 真机验收至少覆盖 Codex、Xcode、Safari、目标应用不在前台、目标无焦点、目标关闭、`Command-Z` 和失败后继续 Talk。

## FRD-20260804-001：空闲灵动岛点击不再展开原有矩形

- 状态：`待验证`
- 首次发现：2026-08-04
- 最近更新：2026-08-04
- 影响范围：App 主工作台、顶部灵动岛、窗口点击路由、界面回归测试
- 关联：Issue #13、Commit `51c38cf`

### 用户现象与影响

用户点击屏幕顶部的空闲灵动岛后，原有矩形不再展开。主窗口已经显示时点击几乎没有可见反馈，使常驻入口表现为失效。

### 环境与复现

- 当前分支为 `codex/13-app-dashboard`，正式运行路径同时包含 Dock 主工作台与顶部灵动岛。
- 启动 Friday，等待灵动岛进入紧凑空闲态，点击顶部灵动岛即可稳定复现。
- 本轮恢复以 `51c38cf^` 中的源码为基线，不使用模型推测重写旧交互。

### 证据

- `51c38cf^` 的 `InputOverlayModel` 包含 `isDashboardExpanded` 与 `expandedPage`，点击命中后由 `expandDashboard()` 展开 `520 x 300` 主页。
- `51c38cf` 删除上述状态与方法，把空闲点击改为 `model.onOpenWorkspace?()`；`FridayApp` 再把该回调连接到主工作台 `show()`。
- 修改后的 `isExpanded` 只对 failure、result 和 notice 返回 true，因此空闲态不可能展开矩形。
- 现有自动测试只验证反馈尺寸和 Dock 重开通知，没有约束“空闲灵动岛点击必须展开”，所以行为变化未被质量门拦截。

### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| Liquid Glass 展开动画失效 | 对照 `InputOverlayRootView.setExpanded` 和 `isExpanded` 调用路径 | 动画代码仍存在，但空闲态从未请求 expanded | 排除 |
| 点击区域没有命中 | 对照全局鼠标监听和 `compactFrameInScreen` | 命中后明确调用 `onOpenWorkspace`，不是无事件 | 排除 |
| 主工作台职责拆分删除了旧入口 | 对照 `51c38cf^..51c38cf` | 展开状态、控制器方法和旧 ContentView 同时被删除 | 确认 |

### 根因

新增 Dock 主工作台时，把“灵动岛职责轻量化”错误实现成“空闲点击改为打开主窗口”，并删除了用户已经验收的历史展开状态链。产品职责调整未经单独确认，同时缺少点击展开回归测试。

### 解决方案

- 从 `51c38cf^` 原样恢复 `InputOverlayExpandedPage`、历史尺寸、`isDashboardExpanded`、`expandDashboard()`、`collapseDashboard()`、设置页切换和点击命中逻辑。
- 从同一提交恢复旧 `ContentView`，仅因当前主窗口已占用名称而改名为 `IslandDashboardView`，并复用字段一致的 `AppDashboardSnapshot`。
- 删除替代旧界面的 `IslandFeedbackView` 和空闲点击打开主窗口的回调；Dock 仍负责重开独立主工作台。
- 恢复旧版尺寸测试并保留新增的 Dock 生命周期测试。

### 验证结果

- `InputOverlay.swift` 与 `51c38cf^` 的历史源码在兼容改名后逐行一致；`IslandDashboardView.swift` 与历史 `ContentView` 在移除已抽离的快照结构并完成兼容改名后逐行一致。
- 独立 DerivedData 与正式 DerivedData 的签名 Debug 构建均成功，确认历史代码可与当前 Dock 主工作台同时编译运行。
- 从正式 DerivedData 启动 Friday 后，真实全局点击空闲紧凑岛成功展开历史 `520 x 300` 主页；没有打开独立主工作台。
- `./scripts/verify.sh` 通过：10 条后端假上游测试和所有可执行 Xcode 测试通过；真实音频设备重启测试按设计跳过，自动门禁未创建 Realtime 凭证或付费回复。
- `git diff --check`、`Info.plist` 和 Xcode 工程文件校验通过。本地服务保持监听，OpenAI 模型元数据检查就绪。
- 设置页切换、外部点击和 `Esc` 收起尚未在本轮逐项人工验收；这些路径直接来自同一历史实现，仍保留为真机检查项，不以构建或静态对比代替。

### 经验与后续

- 新界面入口不能隐式替代已经验收的旧入口；职责拆分和入口删除是两个独立产品决策。
- 视觉状态机测试不能只断言尺寸常量，还要覆盖用户事件触发的状态转换。
- 用户明确要求恢复历史行为时，Git 历史应作为第一手实现证据，兼容修改必须与行为改写分开说明。
