# Friday 工程问题与复盘

> 版本：0.1 · 建立日期：2026-08-03

这份文档记录 Friday 开发中值得复用的问题排查过程和工程经验，服务于后续维护、作品介绍和面试复盘。它不是开发流水账，也不替代 Issue、PR、架构文档或产品路线图。

## 1. 记录目的

每条记录需要让不了解当时上下文的人回答以下问题：

1. 用户实际遇到了什么，影响是什么。
2. 当时掌握了哪些证据，哪些只是猜测。
3. 排查过哪些方向，为什么排除或保留。
4. 根因最终是什么，修复为什么有效。
5. 如何验证，哪些部分仍未验证。
6. 这次经历对后续架构、测试或产品设计有什么可复用价值。

## 2. 什么时候必须记录

出现以下任一情况时，在排查开始时建立记录，并随着证据更新：

- 问题反复出现，或一次排查无法直接定位。
- 涉及多个模块、异步状态、并发、音频、网络、系统权限或外部 Provider。
- 修复过程中出现过有迷惑性的现象、错误假设或无效方案。
- 涉及隐私、API 费用、数据丢失、不可逆操作或安全边界。
- 问题会影响核心用户流程、架构设计或发布判断。
- 解决方案具有作品介绍、面试讲解或后续复用价值。

错别字、纯视觉微调、明确的一行配置修复和没有分析价值的机械维护不单独记录。若小问题暴露了更深层的流程或架构缺陷，则记录深层问题。

## 3. 记录时机与状态

不要等问题解决后凭记忆补写。记录跟随排查过程更新：

```text
发现问题
→ 建立“调查中”条目，写入现象和第一手证据
→ 记录假设、实验与结果
→ 找到根因后更新为“已定位”
→ 修复并验证后更新为“已解决”
→ 真机或生产证据不足时保持“待验证”
```

允许的状态：

| 状态 | 含义 |
| --- | --- |
| `调查中` | 已确认现象，但根因尚未确定。 |
| `已定位` | 根因已有充分证据，修复或验证尚未完成。 |
| `待验证` | 已实现修复，仍缺少必要的真机、权限或真实网络验证。 |
| `已解决` | 修复和约定的验证均已完成。 |
| `暂缓` | 影响和风险已知，当前明确决定不处理，并写明恢复条件。 |

只有证据支持时才能写“根因”和“已解决”。排查中的判断写在“假设与实验”，不能事后删除错误尝试；应简要说明它为什么不成立。

## 4. 与其他文档的关系

| 载体 | 负责回答的问题 |
| --- | --- |
| GitHub Issue | 为什么要做、范围是什么、怎样验收。 |
| 分支与 PR | 具体改了什么、如何审查和回滚。 |
| 产品路线图决策记录 | 为什么选择某个产品或架构方向。 |
| 本文档 | 难点如何出现、如何定位、为何这样修复、学到了什么。 |
| 本地诊断日志 | 某次运行实际发生了哪些事件，作为复盘证据之一。 |

一条复盘可以关联多个 Issue 或 PR，但不复制完整代码差异。长期结论如果改变系统设计，应同步到架构文档；用户行为或阶段门槛变化，应同步到产品路线图。

## 5. 隐私与证据边界

- 不记录 API Key、Token、Authorization header、密码或账号凭证。
- 不粘贴原始音频、完整对话、完整转写、完整截图或用户私有文件内容。
- 日志只摘录定位问题所需的无内容事件、时间、状态、错误码和脱敏字段。
- 外部资料注明来源、访问日期和版本；会变化的信息不写成永久事实。
- 命令输出只保留关键证据，不把大段构建日志复制进文档。
- 无法复现时写明观察范围，不为了让记录完整而虚构根因。

### FRD-20260803-001：本地语音服务监听端口但健康检查超时

- 状态：`已解决`
- 首次发现：2026-08-03
- 最近更新：2026-08-03
- 影响范围：Backend、本地开发流程
- 关联：`Backend/service-manager.mjs`、`Backend/server.mjs`

#### 用户现象与影响

本地服务进程显示仍在运行且 `127.0.0.1:8787` 有监听，但健康检查无法得到响应。Friday 因此不能仅凭端口监听判断语音服务已经可用，可能表现为“进程存在但服务未连接”。

#### 环境与复现

- macOS 本地开发环境。
- 长时间运行的 Node 进程：`Backend/server.mjs`。
- 对 `http://127.0.0.1:8787/health` 发起三秒超时的只读请求。

修改前在重新启动的服务上可以稳定复现：`/health` 会等待 OpenAI 请求，网络不可达时五秒内没有响应。

#### 证据

- `lsof -nP -iTCP:8787 -sTCP:LISTEN` 显示 Node 进程正在监听 `127.0.0.1:8787`。
- `curl --max-time 3 http://127.0.0.1:8787/health` 在三秒内收到 `0` 字节，结果为 `HTTP 000`。
- 隔离的后端 Mock Work API 测试使用随机本地端口可以完成提交、去重、查询和取消。这只能证明对应测试路径可运行，不能证明长期运行的 `8787` 进程健康。
- 源码确认旧 `/health` 路由在发送任何 HTTP 响应前执行 `await checkUpstreamReadiness()`，而上游检查自身最长等待五秒。
- 本次检查没有创建 Realtime 凭证，也没有触发付费模型响应。

#### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 服务根本没有启动 | 检查 TCP 监听和进程 | 端口和进程均存在 | 排除 |
| 后端 Work 路由代码整体无法运行 | 运行隔离的 Mock Work API 测试 | 测试通过 | 对测试覆盖路径排除，不能代表常驻进程 |
| 常驻进程卡住、旧代码未重启或事件循环被阻塞 | 受控重启后再次请求旧 `/health` | 新进程仍因上游请求等待而超时 | 排除“只由旧进程导致” |
| 本地健康端点错误地同步等待 OpenAI | 阅读路由并在网络不可达时分别观察 TCP、HTTP 和上游请求 | 端口已监听，但 `/health` 在上游检查结束前不发送响应 | 确认 |

#### 根因

本地存活与 OpenAI 模型就绪被合并到同一个 `/health` 路由。路由在返回本地状态前同步等待带五秒超时的模型元数据请求；Friday 客户端和管理脚本自身又使用更短超时，因此会先中止并把“上游暂不可达”表现成“本地服务未连接”。

#### 解决方案

- `/health` 只读取本地诊断状态，返回 `upstream_status: "unchecked"`，不访问 OpenAI。
- 新增 `/ready`，只在有边界超时的模型元数据检查通过后返回 ready。
- Friday 客户端改用 `/ready`，因此不会把本地进程存活误报为 Live 可用。
- `npm start` 用 `/health` 判断服务是否已经监听；`npm run status` 和 `doctor` 分开报告本地与模型状态。
- 上游就绪默认三秒超时；成功与失败结果继续使用短期缓存，检查不会创建 Realtime 凭证或模型回复。

#### 验证结果

- 后端假上游测试 `10/10` 通过，包含上游延迟时 `/health` 仍快速返回、`/ready` 有界失败、状态命令分层输出和错误脱敏。
- Swift 客户端定向测试通过，确认模型就绪客户端使用 `/ready`。
- 真实本地服务中，`/health` 约 `6ms` 返回 HTTP 200；当前 OpenAI 网络不可达时，`/ready` 约 `3.0s` 返回 HTTP 503 和脱敏恢复提示。
- `npm run status` 同时输出“Local service: listening”和“OpenAI models: unavailable”，不再混淆两层状态。
- 未创建 Realtime 凭证，未发送音频，也未触发付费模型响应。
- 当前网络路由仍未恢复，因此没有在本轮验证 `/ready` 的真实 HTTP 200；成功路径已由本地假 OpenAI 上游覆盖。

#### 经验与后续

- 进程存在不是服务健康证据，交付检查必须使用有超时的应用层健康请求。
- Liveness 和 Readiness 是不同契约：前者回答进程能否服务，后者回答关键外部依赖能否完成产品请求。
- 客户端超时必须大于服务端上游超时，否则服务端准备好的错误信息会被客户端提前丢弃。
- 自动交付报告继续分开说明“本地服务已监听”和“OpenAI 模型已就绪”，任何一层都不能代替另一层。

### FRD-20260803-002：Talk 音频所有权与 Provider 生命周期耦合

- 状态：`已解决`
- 首次发现：2026-08-03
- 最近更新：2026-08-03
- 影响范围：Talk、Platform、Provider、架构迁移
- 关联：[Issue #8](https://github.com/jason2kkk/Friday/issues/8)、[Issue #6](https://github.com/jason2kkk/Friday/issues/6)

#### 用户现象与影响

当前直接 Realtime Talk 可以运行，但端点、插话和误插话恢复仍需要持续调校。项目希望参考 LiveKit 的 Session Runtime 验证这些能力，同时保留 Friday 原生灵动岛、屏幕框选、Accessibility 和 Work 安全边界。

现有代码让 `ConversationCoordinator` 分别启动本地音频服务和模型 Provider，隐含“Friday 永远自己采集和播放 PCM”。如果直接加入由 SDK 管理麦克风、播放与 AEC 的候选 Runtime，可能产生双重采集、双重回声消除或设备争用，无法进行可信对比。

#### 环境与复现

- 当前分支基于 Phase 3 Alpha 基线。
- 修改前 `ConversationCoordinator.startConversation` 先调用 `audioService.start()`，再调用 `conversationProvider.connect()`。
- 修改前 `finishConversation`、`stop` 分别调用 `conversationProvider.disconnect()` 和 `audioService.stop()`；修改后 Coordinator 只调用 `conversationRuntime.start/stop`。
- LiveKit 仍是候选方案；当前没有引入 SDK、Room、Token 或真实音频测试。

#### 证据

- 当前 `ConversationProviding` 以 `append(AudioChunk)` 和 `assistantAudio(Data)` 表达 App 管理的 PCM 边界。
- 当前 `ConversationAudioServicing` 由 `ConversationAudioService` 实现，并直接拥有 VoiceProcessingIO 或 AVAudioEngine。
- 《LiveKit Talk 技术验证计划》要求第一轮候选验证由 LiveKit Swift SDK 独占设备音频，不能与上述服务并行。
- 本次调查尚未创建 Realtime 或 LiveKit 凭证，也没有触发付费模型响应。

#### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 只增加另一个 `ConversationProviding` 就能安全接入 LiveKit | 对照现有启动顺序和 PCM 事件契约 | Provider 无法阻止 Coordinator 另行启动本地设备音频 | 排除 |
| 让 Coordinator 根据 Provider 类型写条件分支即可 | 评估依赖方向和回滚边界 | Feature 层会知道供应商类型，后续每个 Runtime 都继续扩张条件分支 | 不采用 |
| 抽出同时拥有 Provider、音频端口和启停顺序的 Runtime Session | 用现有 Realtime 包装器和假 LiveKit Transport 做零费用契约测试 | 8 条聚焦测试覆盖两种所有权、启停顺序、失败清理、录制禁用、事件映射与 RPC | 采纳 |

#### 根因

本条没有证明现有语音体验故障由该耦合直接导致；已确认的根因是架构层把会话启停放在 Coordinator，并把物理音频所有权隐式固定为 Friday 本地实现。单独替换 Provider 无法阻止另一套 SDK 再启动设备音频，因此缺少可以原子装配和启停一套 Talk Runtime 的中立边界。

#### 解决方案

已引入 `ConversationRuntimeSession`：由它原子提供 Provider、音频端口、Runtime 描述和统一启停。`DirectRealtimeConversationRuntimeSession` 保持“先本地音频、后 Realtime Provider”的现有顺序，并在失败或取消时统一清理；App 组合根仍只选择这条产品路径。

LiveKit Stage 0 使用假 `LiveKitConversationTransporting`，同一个 Runtime 同时实现 Provider 与音频端口，并以配置校验保证 Runtime 音频独占和 `recordSession=false`。Provider 自管播放通过中立事件进入 Friday 的 Turn/Playback 状态，但不把 PCM 再交给 Friday 播放。ActionProposal/Receipt 只通过带版本和大小上限的 RPC 数据契约传输，不执行动作。

本轮不引入 LiveKit SDK、不替换当前 Talk、不创建真实凭证，也不把 Action 执行权限交给远端 Runtime。

#### 验证结果

8 条 `ConversationRuntimeTests` 已通过，覆盖 Direct Realtime 启停顺序与 Provider 失败清理、LiveKit 禁止录制、单一 Transport 音频所有权、Transport 启动失败清理、Room Token 日志脱敏、ActionProposal/Receipt RPC 往返，以及非法 ID、版本、方法和消息大小拒绝。无签名 Debug 构建、`Info.plist`、工程文件和差异检查通过。

这些自动证据没有访问麦克风、网络、LiveKit Cloud 或 OpenAI，也没有创建凭证和付费响应。尚未引入 LiveKit SDK、真实 Room 或 Agent 进程；真实 `gpt-realtime-2.1` 兼容性、AEC、Adaptive Interruption、延迟、费用和中文对话体验仍未验证，因此条目保持“待验证”。

#### 经验与后续

- 可替换 Provider 不等于可替换 Runtime；谁拥有设备音频、端点和播放回执必须成为显式架构契约。
- 供应商选择应停留在组合根，Feature Coordinator 只依赖中立 Runtime，不能用 Provider 类型判断行为。
- 零费用 Stage 0 只能证明边界可接，不能证明 LiveKit 或 `gpt-realtime-2.1` 的真实兼容性和体验收益。

### FRD-20260803-003：结束 Dictate 时系统表情选择器被 Fn 触发

- 状态：`自动接管已实现，待真机验收`
- 首次发现：2026-08-03
- 最近更新：2026-08-03
- 影响范围：Dictate、Platform、macOS 全局快捷键
- 关联：`Friday/Platform/GlobalHotKeyService.swift`、`Friday/Platform/GlobeKeySystemActionService.swift`、`FridayTests/DictationProviderTests.swift`、`FridayTests/GlobeKeySystemActionServiceTests.swift`

#### 用户现象与影响

用户第一次单击 `Fn` 可以开始转写且不会打开系统表情选择器；录音后第二次单击 `Fn` 确认转写时，Friday 会收到结束动作，但 macOS 同时打开表情选择器。期望两次纯 `Fn` 手势都只由 Friday 处理，不触发系统配置的 Globe/Fn 单击动作。

#### 环境与复现

- macOS 真实设备，Friday 使用 CGEventTap 识别纯 `Fn` 修饰键手势。
- 用户环境为 macOS 27.0，内置键盘的有效 Globe/Fn usage 为 `2`；具体键盘型号尚未采集。
- 用户报告可按“单击 Fn 开始录音，再单击 Fn 结束录音”复现；当前尚未由自动化环境复现系统表情面板。
- 2026-08-03 用户用更新后的构建复验，第二次 Fn 结束转写仍会打开系统表情选择器；上一版尾随 `keyUp` 与异步业务回调修复没有解决真机现象。
- 2026-08-03 用户再次复验 `.cghidEventTap` 构建并提供截图，第二次 Fn 结束转写后字符检视器仍然出现；把 CGEventTap 从 session 前移到 HID 层也没有取消系统 Globe 单击动作。

#### 证据

- `ModifierChordRecognizer` 在纯 Fn 按下时将 `isConsumingFunctionGesture` 设为 `true`，并吞掉候选手势的 `flagsChanged`。
- 释放 Fn 的 `flagsChanged` 会先把 `suppressesCurrentFlagsEvent` 设为 `true`，随后在同一次调用中把 `isConsumingFunctionGesture` 重置为 `false` 并返回 `.dictation`。
- 如果物理 Fn 的 `keyUp` 在释放 `flagsChanged` 之后到达，`GlobalHotKeyService` 此时读取到的 `shouldConsumeFunctionKeyEvent` 已是 `false`，会把该 `keyUp` 放回系统。
- 原有 `testFnOnlyDictationTriggersOnRelease` 只覆盖识别器的 flags 状态，并明确断言释放后 `shouldConsumeFunctionKeyEvent == false`；没有覆盖尾随 Fn `keyUp` 的消费状态。
- CGEventTap 在决定返回 `nil` 前同步调用 `onPressed`。第一次 Fn 进入 `startDictation()` 后把音频启动放入异步 Task；第二次 Fn 进入 `finishDictation()` 后会同步执行 `AVAudioEngine.stop()` 和 `inputNode.removeTap(onBus:)`，因此两次事件回调的执行成本并不对称。
- 查询最近一小时系统日志没有发现 event tap timeout；随后开启约 30 秒 HotKey 实时日志也没有采集到新的 Fn 事件。本轮缺少与用户复现同步的事件流，不能仅凭源码时序断言两个假设中的任意一个是唯一根因。
- 2026-08-03 22:26 与用户复现同步采集到两次完整 Fn：每次只有两个 `flagsChanged`（CGEvent type 12），按下和松开均记录 `consumed=true`，没有任何 Fn `keyDown` 或 `keyUp`。第二次松开后系统仍打开表情面板。

- macOS 27.0 真机只读检查得到 `TISGetFnUsageType() == 2`，且 Carbon 中的 `TISGetFnUsageType` 与 `TISUpdateFnUsageType` 均可动态解析；`com.apple.HIToolbox` 的 `AppleFnUsageType` 显式偏好键当前缺失，因此不能只读 UserDefaults 判断有效动作。

#### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| Fn 释放时过早清理消费状态，导致末尾 Fn `keyUp` 被放行 | 对照识别器状态转换，并增加尾随 `keyUp` 状态测试 | 实时日志确认本机内置键盘不产生 Fn `keyUp`，两次手势都只有 `flagsChanged` | 不是本机现象根因；保留兼容外接键盘的防护 |

#### 根因

根因是 macOS 的单独 Globe/Fn 系统动作不经过应用可取消的 CGEvent 流。Friday 在 session 与 HID 两个 tap 层级都能收到并消费 Fn 的 `flagsChanged`，系统字符检视器仍由 WindowServer 的独立 IOHID 路径打开。尾随 `keyUp` 状态和同步停止音频是值得保留的边界修复，但实时事件证据已经排除它们是本机现象的根因。

#### 解决方案

- 纯 Fn 的释放 `flagsChanged` 触发 Dictate 后保留一次尾随消费状态，只有对应 Fn `keyUp` 到达后才清除；普通键或混合修饰键会取消该状态，不会错误吞掉组合快捷键。
- CGEventTap 只识别并决定是否吞键，随后通过主队列异步调用 `onPressed`，避免在事件回调内同步停止音频或更新界面。
- event tap 被系统禁用时重置识别器并立即重新启用，同时只记录不含用户内容的错误信息，避免残留半个快捷键手势。
- HID tap 真机复验仍无法阻止系统动作，因此恢复权限范围更小的 session tap。
- Friday 获得辅助功能权限后，先持久化接管前的有效 usage 与显式偏好状态，再通过动态解析的 Carbon 接口把当前 Globe/Fn 单击动作临时设为 `0`；用户无需进入系统设置，界面也不提供快捷键修改入口。
- 只有系统动作接管成功后才注册固定 CGEventTap；注册失败会立即注销 tap 并回滚。正常退出恢复原 usage 和原偏好状态；恢复未完成时保留凭据，下次启动不会把 Friday 留下的 `0` 错认成用户原设置。

### FRD-20260803-004：Talk 本地停说后一直停留在收听状态

- 状态：`历史 client-gate 方案已实现，已被 FRD-20260804-008 取代`
- 首次发现：2026-08-03
- 最近更新：2026-08-04
- 影响范围：Talk、Platform、Realtime Provider、用户 Turn 状态
- 关联：[Issue #10](https://github.com/jason2kkk/Friday/issues/10)、`Friday/Platform/ConversationAudioService.swift`、`Friday/Features/ConversationCoordinator.swift`

#### 用户现象与影响

用户在 Talk 中说了多段话并停下，灵动岛持续显示收听状态，超过一分钟仍没有回复，只能手动结束会话。这会让用户误以为网络或模型没有收到语音，实际回复请求根本没有被创建。

#### 环境与复现

- 真实 Mac、VoiceProcessingIO 全双工 AEC、蓝牙输入/输出设备。
- 故障构建使用 `gpt-realtime-2.1`、`near_field` 和 high-eagerness semantic VAD，服务端自动回复关闭，由客户端在 Provider 端点后创建回复。
- 诊断会话：`2cd3ada7-4dbc-4b81-ba3c-a77bf4930952`，2026-08-03 21:16:19 至 21:17:38。
- 用户说话并停下后可以稳定观察到本地释放事件，但没有 Provider 停说事件。
- 首次修复后真机复验会话：`0522c9d0-2ac7-4219-b149-773a6ed1101b`，2026-08-03 23:31:30 至 23:31:58。用户第二轮要求在 Codex 输入框写入 `1234`。

- 23:31 真机复验中，第一轮正常产生 `speech_stopped`、`response.create` 和语音回复，证明同一会话的 WebSocket 与模型不是全程不可用。
- 第二轮本地于 23:31:50.308 首次释放，短暂续说后于 23:31:54.062 再次释放；四秒静音尾于 23:31:58.073 耗尽，Provider 始终没有返回 `speech_stopped`。
- 该轮没有任何 `toolCall`、`tool.resolved` 或 `tool.output_sent`。因此这次“没有成功”发生在语音端点阶段，不是 Codex 别名解析、Accessibility 定位或写入执行被拒绝。
- 官方文档确认 `create_response=false` 只关闭 VAD 后的自动回复，仍应保留 VAD 的语音开始、结束和自动 commit 行为；当前证据不足以解释为配置上主动禁用了端点。
- 2026-08-04 再次核对 OpenAI 官方 Realtime VAD 与 Conversation 指南：客户端可以设置 `turn_detection=null` 关闭 VAD；该模式下由客户端在音频结束后显式发送 `input_audio_buffer.commit`，再发送 `response.create`。`input_audio_buffer.clear` 可只清理尚未提交的当前输入缓冲。

#### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 网络或 API Key 失效导致没有回复 | 对照同会话开场回复、WebSocket 生命周期和错误事件 | 开场回复正常，连接保持约 75 秒且无失败事件 | 排除 |
| 模型已开始生成但回复被播放层丢失 | 查找用户 Turn 后的 Response、Assistant Item 和音频事件 | 用户 Turn 后没有创建 Response | 排除 |
| 本地输入门先停止上传，使 semantic VAD 缺少形成端点所需的连续静音 | 对齐本地 release、Provider stop 和音频门返回路径 | 原始实现确实在 release 后停止输出；补送四秒零值 PCM 后第一轮成功、第二轮仍失败 | 是原始问题之一，但不是完整根因 |
| 直接在 VAD 开启时手工 commit 可以安全兜底 | 查询官方 Realtime 文档 | 官方把 commit 明确放在 VAD 关闭流程；混用会引入竞态 | 不采用 |
| 四秒零值 PCM 一定会让 semantic VAD 结束每一个 Turn | 用真实多轮中文对话对照 Provider 端点时间 | 同一会话第一轮成功、第二轮耗尽仍无 `speech_stopped` | 排除；需继续记录实际上传帧数与 Provider 事件 |
| 本地门已经形成可靠端点后仍必须等待 Provider 第二次判断 | 对照两层状态机和官方关闭 VAD 的手工提交路径 | 第二层不返回会确定性阻止 `response.create`；官方支持单一客户端端点 | 确认为架构根因，取消双重端点所有权 |

#### 根因

根因是端点所有权被拆给了两个相互依赖的判断器：本地输入门先决定哪些声音可上传、何时释放，Coordinator 却只在 Provider semantic VAD 再次返回 `speech_stopped` 后才创建回复。第二层没有端点时，即使音频、连接和模型都正常，第一层已经确认的有效用户 Turn 也不会进入 `response.create`。补送零值 PCM 只能提高第二层成功概率，不能消除这项不可靠依赖。

#### 解决方案

- 后端 Talk 配置设置 `turn_detection=null`，并通过短期凭证元数据明确声明 `endpointing=client_gate`。
- 本地输入门的 `speechConfirmed` / `speechReleased` 直接驱动 Friday Turn；Provider speech-start/stop 在该模式下不再驱动状态，避免重复端点。
- 本地释放后保留 450ms 续句窗口；最终提交时先刷新未满包 PCM，再通过同一串行输入队列发送 `input_audio_buffer.commit` 和 `response.create`。
- `input_audio_buffer.committed` 返回的 Provider Item ID 会附着到客户端已经建立的 Turn，不再反向创建新的用户 Turn。
- 端点异常只取消当前待回复 Turn、发送 `input_audio_buffer.clear`、重置本地输入并回到收听，不结束整段 Talk。
- 框选和截图确认期间同步缓存音频与客户端端点事件；成功后先重放音频再重放端点，取消或失败则一起丢弃并重置输入门。

#### 验证结果

- 10 条 Backend 假上游测试通过，确认 Talk 凭证的 `turn_detection=null`、`endpointing=client_gate` 和现有工具/安全参数。
- 43 条 `TalkInteractionTests` 定向测试通过，覆盖无 Provider speech 事件仍只创建一次回复、450ms 内续说取消、`append -> commit -> response.create` 顺序、端点异常保持会话、committed Item 关联和框选期间语音恢复。
- 自动测试没有访问麦克风、OpenAI 或真实网络，没有创建 Realtime 凭证和付费响应。
- 新客户端端点方案尚未完成真实中文多轮复验，不能把聚焦测试通过视为真机问题已解决。

#### 经验与后续

- 本地 VAD 与云端 VAD 不能各自拥有同一轮的最终裁决；端点所有权必须是 Runtime 契约的一部分。
- Mock 直接发出 `speech_stopped` 只能验证旧状态机收到端点后的行为，不能证明真实音频一定能产生端点。
- 音频交互测试至少要覆盖“最后一个真实语音帧之后发送了什么”，以及发送顺序，否则最基础的停说失败会被事件级单测掩盖。
- 屏幕上下文等短事务不能只缓存音频而丢失端点状态；跨事务恢复必须把数据和控制事件作为一个整体。

#### 后续架构结论（2026-08-04）

- 这一条目保留了“本地门先停止上传，Provider VAD 却继续等待”的真实故障证据；不删除历史实验或把后续方案倒写成当时已知。
- `client_gate` 消除了双重端点互相等待，但后续户外真机证据又证明音量启发式本地门无法可靠区分动态风声、车流、人群背景与真实用户话语。
- 因此产品默认已迁移到 FRD-20260804-008 的 Provider `semantic_vad` 单一所有权方案；本条的 `client_gate` 仅作显式开发回退和故障对照。

- 2026-08-06 真机 trace 共出现 3 次 `open_application`：1 次在 `479ms` 内成功，2 次约 `4.1s` 后以 `application_activation_failed` 失败；同一会话没有任何 `write_focused_input` 调用。失败发生在本地前台应用复验，且当前诊断没有记录激活阶段，不能据此断言是应用名、Bundle、进程切换还是 LaunchServices 路径失败。

#### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 只在 Prompt 中要求模型“识别 Codex”即可安全执行 | 对照本地运行应用和 Bundle ID | 模型名称不能证明目标进程身份，也不能验证输入框 | 排除 |
| 复用后台 Work 提交路径处理一次文字写入 | 对照生命周期与权限 | 可撤销即时写入不需要排队、持久化或二次确认，进入 Work 会不必要地阻塞交互 | 不采用 |
| Realtime 解释文字和应用意图，本机生成 ActionProposal 并执行 | 用 Codex 别名、通用应用、显式目标优先、失败与重复 Tool Call 测试 | 目标身份和执行证据都留在可信本地层，Talk 仍保持连接 | 采纳 |
| 灰色声波是模型或网络延迟造成 | 对照 Presentation 状态映射 | 准备态明确使用 idle source，音频态才使用 assistant source | 排除网络根因，修复状态映射 |

#### 根因

产品已经有“模型提出 Action、客户端凭回执确认执行”的目标架构，但实际 Talk 仍只接入 Mock Work 工具，缺少即时可撤销写入的 Tool Intent Bridge、本机应用身份解析和 ActionExecutor。与此同时，Prompt 过宽，允许模型用重复复述和能力介绍填充回复；后续为了控成本设置的 220 token 硬上限又会截断正常回答；Presentation 又把同一个 Assistant 回合拆成两种颜色来源。

#### 解决方案

- 后端始终向 Talk 暴露 `write_focused_input(text, application?)`，而依赖 final ASR 的 Work 工具继续保持关闭。
- `ConversationActionBridge` 校验参数、生成 `reversibleLocalWrite` ActionProposal，并按 Tool Call ID 缓存输出，避免重复执行。
- `RunningApplicationResolver` 使用运行应用、显示名、Bundle ID 和有限别名解析用户原话；显式应用优先于 Talk 启动时锁定的目标，未知或歧义结果不回退。
- `FocusedInputActionExecutor` 只接受无需确认、可撤销的文字写入，复验目标后复用剪贴板粘贴路径，并返回 `succeeded/failed/unknown` ActionReceipt。
- Talk 不再默认设置额外 `max_output_tokens` 硬上限；普通回复、开场问候、工具跟进和 Work 结果语音都由 Prompt 控制简洁度，不由 Friday 额外截断。Prompt 禁止复述、能力介绍和工具前口播，写入成功后只说“写好了”。
- Assistant 准备态直接使用静止粉色声波，真实音频到达后只改变高度，不再经历灰色到粉色。
- 2026-08-05 补充：Talk 启动锁定和指定应用执行统一采用受约束的 Action 目标解析。先读取键盘焦点；只有指定应用仍是前台应用且鼠标命中的可编辑元素属于同一 PID 时才使用指针目标，密码框、跨应用命中和无法验证的控件继续拒绝。
- Action 回执与 Talk trace 增加不含正文、应用私有内容和坐标的失败码，区分目标未聚焦、权限拒绝、密码框、焦点恢复失败、粘贴事件失败等本地阶段。
- 2026-08-05 跨应用补充：新增 `open_application` 本地工具；`RunningApplicationResolver` 从运行进程和标准 Applications 目录中的 Bundle 解析目标，启动或激活后复验前台 PID。指定应用写入复用同一激活路径，并在约两秒的有限窗口内等待 Accessibility 目标就绪；不存在、歧义、激活失败或始终无可验证输入目标时返回脱敏失败码，不回退到其他应用。
- 2026-08-06 追加修复目标：运行中应用先尝试系统激活，失败后再通过同一 Bundle URL 请求 LaunchServices 置前，并允许进程重启后用相同 Bundle ID 更新目标 PID；新增微信别名。指定应用没有标准焦点时，只允许选择前台窗口中唯一的非密码可编辑控件，不按坐标或视觉猜测多个候选。
- 2026-08-06 实现结果：本地执行器将激活失败细分为进程不可用、LaunchServices 启动失败和前台超时；指定应用写入等待窗口扩大到约三秒，并把 `accessibility_permission` 以 `granted/denied/unknown` 写入工具回执。单独打开应用返回 `not_required`，因为置前本身不需要辅助功能权限。后端 Prompt 明确“打开并写入”只调用 `write_focused_input`，其成功回执也要求模型继续完成同一请求中的写入。
- Prompt 必须明确：同一请求只要包含写入正文，就直接调用 `write_focused_input(application:)`，不得先以 `open_application` 结束；打开工具的回执也应提醒模型继续完成原请求中的写入步骤。

### FRD-20260804-006：Talk 实时字幕延迟与费用边界验证

- 状态：`代码已完成，待真机延迟验收`
- 首次发现：2026-08-04
- 最近更新：2026-08-04
- 影响范围：Realtime 输入转写、Talk Turn 关联、灵动岛展开页、额外转写费用

#### 用户现象与影响

用户希望在 Talk 界面中像双方聊天一样实时看到自己和 Friday 的内容，但如果用户说话后文字出现明显滞后，这项交互就没有实际价值。现有代码只消费最终用户转写，并忽略助手转写增量，无法从 UI 观察真实延迟。

#### 证据与假设

- OpenAI Realtime 官方文档提供 `conversation.item.input_audio_transcription.delta` 和 `completed` 事件；`minimal` 是优先降低延迟的转写档位，但官方不承诺固定毫秒值。
- Provider 已按 `item_id` 关联最终转写，Coordinator 已有 Friday TurnID 映射，可以沿用同一身份链过滤迟到事件。
- 假设 `gpt-live-transcribe` 的增量在当前网络和真实麦克风下足够接近无感；该假设只能通过真机数据确认，自动测试不能证明。

#### 实施方案

- 接入用户转写 delta，并与 final 一起按当前 Turn 和 Provider Item 过滤；旧轮次、播放残留和被替换轮次不更新 UI。
- 用户 partial、助手 delta 和最近一轮文字只保留在内存，不进入日志、历史、记忆或 Work；Work 仍只使用 final transcript。
- 展开灵动岛显示当前双方字幕，并展示“首段已转发音频到首字”“连续 delta 间隔”和“停说到定稿”的毫秒读数。

#### 用户现象与影响

#### 当前证据

- 本地服务 `/health` 与 `/ready` 均可用，当前报告 `Dictate/Talk: gpt-realtime-2.1`，并为 Talk 额外启用 `gpt-live-transcribe`。

#### 根因判断

高置信度根因是 Dictate 把“整理结果”和“原始语音核对转写”绑定成了一个完成条件。修复后 Dictate 不再声明该通道，因此 `response.done` 可以直接进入本地输出校验；`gpt-live-transcribe` 仍只对 Talk 字幕、WorkDraft 的最终用户原话核对有价值。网络或模型延迟仍可能存在，需要用新增阶段日志区分。

#### 开源项目对照

- [KeyScribe](https://github.com/rsperko/keyscribe)（GPL-3.0）：把本地/流式 STT、可选 rewrite、确定性校验和原文回退拆开；rewrite 超时或校验失败只回退本地文本，不阻塞交付。其 prompt 设计使用稳定 system 规则、`<instructions>/<context>/<content>` 数据隔离、sentinel token 和固定语料评测。这里只借鉴设计，不复制 GPL 代码。
- [WhisperDictate](https://github.com/jerryshimax/whisper-dictate)（MIT）：用本地 VAD 把长录音切成 speech segment，在用户仍然说话时后台转写；先做快速正则清洗，LLM polish 是可选后处理，尾部只处理剩余音频。
- [OpenFlow](https://github.com/Krishiv-Thakuria/openflow)（MIT）：录音、转写、清洗、写回是单向状态机；LLM polish 有 5 秒硬超时，失败或超时立即使用已有转写结果。
- [VoiceInk](https://github.com/sophiamaxwell/voiceink)（未声明 SPDX license）：本地 WhisperKit、菜单栏常驻和统一写回，强调输入交付链路而不是额外对话模型。

这些项目的共同可复用原则是：基础转写先可交付，润色和校验只能改善结果，不能让用户无限等待；prompt 负责约束行为，确定性校验负责兜底。

#### 建议修复方案

1. 已完成：Dictate credential 不再声明 `audio.input.transcription`，`input_transcription_enabled` 按 mode 返回；Talk 继续按配置启用该通道。
2. 已完成：Dictate 的 `response.done` 直接进入本地输出校验和写回，不等待额外 ASR；Talk 仍可使用最终输入转写做字幕和 WorkDraft 事实来源。

### FRD-20260804-011：Talk 对话链路复审发现播放期静音与工具回执重复响应

- 状态：`追加修复中`
- 首次发现：2026-08-04
- 最近更新：2026-08-06
- 影响范围：Talk 音频上行、主动插话、工具回执、Realtime WebSocket 实时性、真机体验验收

#### 复审结论

本次复审没有把“本地服务正在监听”误当作“自然对话已经稳定”。Backend `/health` 与 `/ready` 正常，最近脱敏 Talk trace 也能看到首段音频；但 Talk 仍有两个会直接影响产品可用性的结构性问题：

1. Provider-VAD 播放期间，Friday 完全停止向 Realtime 上传麦克风音频，因此用户无法真正主动打断正在播放的回复。当前 `interrupt_response=false` 与播放期静音策略共同形成“只防误打断、不支持插话”的行为，和 Prompt 中“用户可以随时打断”不一致。
2. 普通工具回执无条件以 `createsResponse=true` 发送。工具执行失败后仍会请求一次新的语音回复，造成用户看到失败后又听到额外一句话或状态跳回收听。最近 trace 已实际出现 `tool.resolved(status=failed)` → `tool.output_sent(creates_response=true)` → `response.started(source=provider_initiated)`。

2026-08-05 对最新真实 trace 重新按事件顺序检查后，又确认了三个不能归为网络问题的客户端缺陷：

3. 播放期噪声虽然被标记为 `interruption.rejected`，客户端也删除了对应用户音频 Item，但 Provider 的 `semantic_vad` 使用 `create_response=true`，因此该 Item 的自动 Response 仍会创建。真实顺序为 `interruption.rejected` → `turn.suppressed_audio_discarded` → `input_audio_buffer.committed` → 新的 `response.started(source=provider_initiated)`，并最终播放了用户没有请求的回复。
4. 工具型 Response 完成时，Coordinator 在本地 Action 解析结束前立即从 `assistant_preparing` 切回 `listening`；工具回执随后又创建一个 Follow-up Response，使灵动岛先显示灰色收听态、约数百毫秒后再回到回应态，并在中间错误开放麦克风上行。
5. `RealtimeConversationProvider.connect()` 在 WebSocket `resume()` 后立即返回，没有等待 `session.created/session.updated`。Coordinator 因而可能在 Realtime 会话真正可用前显示收听态；最近 trace 中本地音频启动约 `659ms`、凭证与 WebSocket 建立约 `1.10s`，之后仍等待约 `1.54s` 才收到 `provider.session_ready`。
6. Talk 面板的费用只累计 `gpt-realtime-2.1` Response usage，没有累计独立启用的 `gpt-live-transcribe`。OpenAI 官方价格页在 2026-08-05 列出的 `gpt-live-transcribe` 价格为 `$0.017 / minute`；当前展示因此低估真实费用。
7. 2026-08-05 复核 OpenAI 官方 Realtime VAD 文档确认：对话模式的 `semantic_vad` 明确支持 `interrupt_response=true`，用于在检测到用户语音时中断正在进行的模型 Response。当前无法插话不是 `gpt-realtime-2.1` 的能力限制，而是 Backend 固定返回 `false`、客户端播放期完全停止上行共同造成的产品配置限制。
8. 2026-08-06 最新 245 事件真机 trace 中，连续三次主动插话均得到本地确认并停止播放，旧的“第二次无法打断”没有复现；但启动连接期已有本地确认语音时仍发起开场问候，问候和随后第一轮回复又被 Provider 的自动中断取消。官方 Realtime VAD 文档确认 `interrupt_response` 是对话模式的 Provider 配置；当前将“允许客户端受控插话”与“Provider 一检测到语音就自动取消”绑定为同一个布尔值，绕过了本地 AEC/近场确认边界。

#### 本轮修复范围（2026-08-05）

- 为已明确拒绝并提交的 Provider 用户音频 Item 建立带身份和短时有效期的 Response 拒绝记录；只取消与该记录紧邻的自动 Response，并屏蔽其迟到音频/完成事件，不无限期盲目取消下一次合法回复。

- Realtime Provider 的 `connect()` 等待实际 `session.created/session.updated`，并设置有界超时；Coordinator 不再把单独收到 Provider 事件提前解释为完整 Runtime 已就绪。
- 会话账本把带 `audioSeconds` 的 `gpt-live-transcribe` usage 按官方每分钟价格计入 Talk 合计估算，同时保留 Realtime token 统计口径。
- 为上述真实事件顺序增加聚焦回归测试；自动测试仍不能替代真实麦克风、扬声器回采和环境噪声验收。

### 用户现象与影响

产品目标已经明确为“用自然语言控制电脑并完成文件、浏览器和跨应用任务”，但实现和文档仍主要围绕 Dictate、Talk、框选、应用激活和输入框写入推进。用户多次要求 Agent 完成普通桌面任务时，系统只能调用两个局部本地 Action 或返回找不到焦点，形成“语音 Agent 已实现”的预期与实际能力不一致。

### 证据

- 当前真实本地执行能力只有 `open_application` 与 `write_focused_input`；它们没有通用应用/窗口观察、点击、滚动、快捷键、文件、Shell 或浏览器执行器。
- 当前 Backend Work 使用内存 Store 和 `mock_read_only` executor，没有真实 Planner、Capability Router 或多步骤动作后验证循环。
- 旧产品路线把输入框、语音、屏幕和 Agent 写成依次完成的 Phase；旧实施顺序又把 Conversation、Memory 和 Mock Work 放在真实 Computer Use 验证之前。
- Conversation 与 Work、ActionProposal 与 ActionReceipt、权限分级和异步交付等底层契约已经存在，说明问题不是需要推翻全部架构，而是北极星、完成定义和实施顺序没有随最终产品目标同步。

### 假设与核对

| 假设 | 核对方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 只要继续增加应用别名和焦点兜底，就能逐步得到通用 Agent | 对照目标任务所需能力与当前执行器 | 文件、浏览器、多步骤观察和验证仍完全缺失 | 排除 |
| Dictate、Talk、屏幕理解必须全部体验完美后才能开始 Agent | 检查生命周期和依赖 | 文字 Work 测试台可以独立验证 Planner 与 Computer Use，且不会改变语音入口 | 排除 |
| 现有 Conversation/Work 架构需要全部重做 | 检查运行时契约和当前代码 | 异步 Work、动作提议、回执与权限边界可以直接复用 | 排除 |
| Realtime 工具调用等于 Agent | 检查现有工具链 | 只有单步 Action，没有 `Observe -> Plan -> Act -> Verify` | 排除 |

### 根因

最初“先验证输入框写回”的 MVP 选择在当时范围内合理；偏差发生在产品目标扩展为通用桌面 Agent 后，权威路线和工程完成定义没有同步回正。团队继续按旧 Phase 优化入口，并把两个 Realtime 工具调用称为 Agent，导致局部功能进展掩盖了执行核心仍不存在的事实。

### 解决方案

- 新增《通用 Agent 产品与实施路线》作为当前产品北极星和实施主线。
- 明确 Dictate 是快速路径，Conversation 是前台入口，Work 是后台生命周期，Agent 是 Work 内部的观察、规划、执行和验证循环。
- 后续先收口基线，再用文字任务台验证 Computer Use Runtime 和单一 Planner；首个任务固定为 TextEdit 新建、写入、保存与读回。
- 工具按文件/受限 Shell、浏览器 DOM/CDP、App API/AX 和视觉 Computer Use 分域路由，不再为具体应用持续增加特例。
- Cua Driver 只作为待验证候选；签名、macOS 14、TCC 权限归属、生命周期和真实 App 行为通过前不承诺正式依赖。
- 更新 AGENTS、README、产品路线、架构概览、技术架构、交互架构和文档索引，防止后续任务重新回到旧实施顺序。

### 验证结果

- 文档已经统一到同一北极星和 Milestone 顺序；旧 Phase 明确标记为历史记录。
- 已明确写下当前事实：语音入口和部分本地 Action 已实现，通用 Agent 执行核心尚未实现。
- 本次没有修改运行代码，没有创建 Realtime 凭证、发送音频或触发付费模型响应。
- Computer Use 候选、Planner 闭环和 TextEdit 退出任务仍需后续独立 Issue、分支、自动契约测试和真实 Mac 验收，因此本条不标记“已解决”。

### 经验与后续

- 产品北极星变化时，必须同步修改完成定义和实施顺序，不能只在讨论中改变目标。
- “模型调用工具”只证明路由存在；只有观察、规划、多步执行、动作后验证和真实结果交付同时成立，才能称为 Agent 闭环。
- 音频体验测试与执行器测试应分开；先用文字任务复现能够显著缩短定位路径。
- 下一个 Agent 工作必须是独立 Computer Use Issue，不继续扩大当前 focused-input 分支。

## FRD-20260806-002：Computer Use 候选依赖与首个可验证闭环

- 状态：`实现完成，待真机验收`
- 首次发现：2026-08-06
- 最近更新：2026-08-06
- 影响范围：Computer Use、macOS 权限、分发、Agent 工作台、文件验证
- 关联：GitHub Issue #18、`codex/18-computer-use-smoke-task`

### 用户现象与影响

路线已经要求先完成 TextEdit 新建、写入、保存和读回，但仓库中只有单步应用激活和输入框写入，没有独立 Computer Use Runtime、能力目录、动作后重观察、取消或最终文件证据。若直接把 Cua Driver 当成既定依赖，又会提前引入嵌套二进制签名、TCC 权限归属和分发风险。

### 证据与判断

- Cua Driver 0.18.0 是 MIT Rust workspace，可构建 `cua-driver` CLI/daemon，并通过私有 Socket 和 stdio MCP 接入；它不是 Swift Package。
- 上游嵌入文档要求签名 GUI App 直接启动 daemon，不能经 `NSWorkspace` 或独立 gateway；其 TCC responsibility chain 说明尚未在 Olli 的签名 App 中实测。
- 正式采用前仍需验证 arm64/Universal 构建产物、嵌套签名、公证、macOS 14、包体、helper 生命周期、崩溃恢复和真实应用权限体验。
- 因此本 Issue 不提交第三方二进制，先建立 Olli 自有中立契约并用原生 macOS Adapter 完成同一退出任务；后续 Cua 或自研执行层都必须实现该契约。
- 完整门禁后的源码复查发现，首版 TextEdit AppleScript 把 Swift 路径转义函数名原样放入脚本，且合成快捷键只发送修饰键按下事件、没有给主键设置 flags；这两项都会让自动测试通过但真机保存链路不可靠。

### 实现

- 新增 `ComputerUseRuntime`、最小 `CapabilityRegistry`、`ComputerUseObservation`、动作效果和独立 `Verification` 状态。
- `TextEditSmokeTaskRunner` 按固定计划执行，每个动作后重新观察，允许中间键盘投递保持 `unverifiable`，但只有最终 UTF-8 文件内容精确一致才返回成功。
- `NativeComputerUseRuntime` 只允许 Olli 的 `AgentSmokeTests` 目录，拒绝覆盖已有文件；通过应用激活、CGEvent、TextEdit Automation 和 FileManager 读回完成首个本地任务。
- TextEdit 保存脚本现在插入经过 AppleScript 转义的真实 POSIX 路径，并显式使用 TextEdit 的 `as "text"` 保存形式；合成文字同时发送 key-down/key-up，合成快捷键在主键事件上显式设置 Command/Shift/Option/Control flags。
- 主工作台新增 Agent 文字任务页，显示固定目标、文件路径、当前步骤和取消入口；未接入 Realtime Prompt 或真实 Planner。

### 验证结果

- `ComputerUseRuntimeTests` 5/5 通过，覆盖能力 ID、每步重观察、最终验证门槛、拒绝停止、`unknown` 不成功和取消；使用完整 Xcode 目标而非 CommandLineTools。
- 签名 macOS Debug 测试构建通过，`scripts/verify.sh`、`plutil` 与 `git diff --check` 通过；TextEdit 保存脚本另以 `osacompile` 独立编译通过；Backend 本地服务和模型元数据检查通过；未创建 Realtime 凭证、发送音频、截图或触发模型费用。
- 尚未点击工作台真实运行 TextEdit 任务，因此 Automation 权限提示、TextEdit 纯文本保存行为、实际文件内容和取消时机仍待签名 Debug App 真机验收。

### 可复用结论

- 第三方执行器应替换 Platform Adapter，而不是改变 UI、Work、Planner 或验证契约。
- “键盘事件已发送”只能记为 `unverifiable`；后续可观察的文件、窗口、AX 或 DOM 后置条件才允许任务完成。
- 首个任务保持固定计划是为了隔离执行器问题；真实 Planner 属于下一阶段，不能把固定 Runner 描述为通用 Agent。
