# Friday 工程问题与复盘

> 版本：0.1 · 建立日期：2026-08-03

这份文档记录 Friday 开发中值得复用的问题排查过程和工程经验，服务于后续维护、作品介绍和面试复盘。它不是开发流水账，也不替代 Issue、PR、架构文档或产品路线图。

## 1. 记录目的

每条记录需要让不了解当时上下文的人回答以下问题：

1. 用户实际遇到了什么，影响是什么。
2. 当时掌握了哪些证据，哪些只是猜测。
3. 排查过哪些方向，为什么排除或保留。
4. 根因最终是什么，修复为什么有效。
5. 如何验证，哪些部分仍未验证。
6. 这次经历对后续架构、测试或产品设计有什么可复用价值。

## 2. 什么时候必须记录

出现以下任一情况时，在排查开始时建立记录，并随着证据更新：

- 问题反复出现，或一次排查无法直接定位。
- 涉及多个模块、异步状态、并发、音频、网络、系统权限或外部 Provider。
- 修复过程中出现过有迷惑性的现象、错误假设或无效方案。
- 涉及隐私、API 费用、数据丢失、不可逆操作或安全边界。
- 问题会影响核心用户流程、架构设计或发布判断。
- 解决方案具有作品介绍、面试讲解或后续复用价值。

错别字、纯视觉微调、明确的一行配置修复和没有分析价值的机械维护不单独记录。若小问题暴露了更深层的流程或架构缺陷，则记录深层问题。

## 3. 记录时机与状态

不要等问题解决后凭记忆补写。记录跟随排查过程更新：

```text
发现问题
→ 建立“调查中”条目，写入现象和第一手证据
→ 记录假设、实验与结果
→ 找到根因后更新为“已定位”
→ 修复并验证后更新为“已解决”
→ 真机或生产证据不足时保持“待验证”
```

允许的状态：

| 状态 | 含义 |
| --- | --- |
| `调查中` | 已确认现象，但根因尚未确定。 |
| `已定位` | 根因已有充分证据，修复或验证尚未完成。 |
| `待验证` | 已实现修复，仍缺少必要的真机、权限或真实网络验证。 |
| `已解决` | 修复和约定的验证均已完成。 |
| `暂缓` | 影响和风险已知，当前明确决定不处理，并写明恢复条件。 |

只有证据支持时才能写“根因”和“已解决”。排查中的判断写在“假设与实验”，不能事后删除错误尝试；应简要说明它为什么不成立。

## 4. 与其他文档的关系

| 载体 | 负责回答的问题 |
| --- | --- |
| GitHub Issue | 为什么要做、范围是什么、怎样验收。 |
| 分支与 PR | 具体改了什么、如何审查和回滚。 |
| 产品路线图决策记录 | 为什么选择某个产品或架构方向。 |
| 本文档 | 难点如何出现、如何定位、为何这样修复、学到了什么。 |
| 本地诊断日志 | 某次运行实际发生了哪些事件，作为复盘证据之一。 |

一条复盘可以关联多个 Issue 或 PR，但不复制完整代码差异。长期结论如果改变系统设计，应同步到架构文档；用户行为或阶段门槛变化，应同步到产品路线图。

## 5. 隐私与证据边界

- 不记录 API Key、Token、Authorization header、密码或账号凭证。
- 不粘贴原始音频、完整对话、完整转写、完整截图或用户私有文件内容。
- 日志只摘录定位问题所需的无内容事件、时间、状态、错误码和脱敏字段。
- 外部资料注明来源、访问日期和版本；会变化的信息不写成永久事实。
- 命令输出只保留关键证据，不把大段构建日志复制进文档。
- 无法复现时写明观察范围，不为了让记录完整而虚构根因。

## 6. 条目模板

新增记录时复制下面模板。编号格式为 `FRD-YYYYMMDD-NNN`，同一天从 `001` 递增。

```markdown
## FRD-YYYYMMDD-NNN：问题标题

- 状态：调查中 / 已定位 / 待验证 / 已解决 / 暂缓
- 首次发现：YYYY-MM-DD
- 最近更新：YYYY-MM-DD
- 影响范围：Dictate / Talk / Agent / Platform / Backend / 工程流程
- 关联：Issue、PR、Commit、日志或文档；没有则写“待创建”或“不适用”

### 用户现象与影响

描述用户能观察到的实际行为、期望行为和影响，不先写技术结论。

### 环境与复现

记录系统、构建、触发条件、复现频率和最小步骤。无法稳定复现时明确说明。

### 证据

按时间列出日志事件、命令结果、源码位置或真机观察，并区分自动检查与人工验收。

### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 示例假设 | 执行的最小实验 | 观察结果 | 保留 / 排除 / 证据不足 |

### 根因

只有在证据充分后填写。调查中写“尚未确定”。

### 解决方案

说明修复策略、关键取舍、为什么选择它，以及明确没有做什么。

### 验证结果

列出自动测试、构建、真实 Mac 验收和仍未覆盖的场景。

### 经验与后续

总结可以迁移到其他模块或面试讲解的经验，并列出需要同步到架构、测试或产品文档的动作。
```

## 7. 问题记录

### FRD-20260803-001：本地语音服务监听端口但健康检查超时

- 状态：`已解决`
- 首次发现：2026-08-03
- 最近更新：2026-08-03
- 影响范围：Backend、本地开发流程
- 关联：`Backend/service-manager.mjs`、`Backend/server.mjs`

#### 用户现象与影响

本地服务进程显示仍在运行且 `127.0.0.1:8787` 有监听，但健康检查无法得到响应。Friday 因此不能仅凭端口监听判断语音服务已经可用，可能表现为“进程存在但服务未连接”。

#### 环境与复现

- macOS 本地开发环境。
- 长时间运行的 Node 进程：`Backend/server.mjs`。
- 对 `http://127.0.0.1:8787/health` 发起三秒超时的只读请求。

修改前在重新启动的服务上可以稳定复现：`/health` 会等待 OpenAI 请求，网络不可达时五秒内没有响应。

#### 证据

- `lsof -nP -iTCP:8787 -sTCP:LISTEN` 显示 Node 进程正在监听 `127.0.0.1:8787`。
- `curl --max-time 3 http://127.0.0.1:8787/health` 在三秒内收到 `0` 字节，结果为 `HTTP 000`。
- 隔离的后端 Mock Work API 测试使用随机本地端口可以完成提交、去重、查询和取消。这只能证明对应测试路径可运行，不能证明长期运行的 `8787` 进程健康。
- 源码确认旧 `/health` 路由在发送任何 HTTP 响应前执行 `await checkUpstreamReadiness()`，而上游检查自身最长等待五秒。
- 本次检查没有创建 Realtime 凭证，也没有触发付费模型响应。

#### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 服务根本没有启动 | 检查 TCP 监听和进程 | 端口和进程均存在 | 排除 |
| 后端 Work 路由代码整体无法运行 | 运行隔离的 Mock Work API 测试 | 测试通过 | 对测试覆盖路径排除，不能代表常驻进程 |
| 常驻进程卡住、旧代码未重启或事件循环被阻塞 | 受控重启后再次请求旧 `/health` | 新进程仍因上游请求等待而超时 | 排除“只由旧进程导致” |
| 本地健康端点错误地同步等待 OpenAI | 阅读路由并在网络不可达时分别观察 TCP、HTTP 和上游请求 | 端口已监听，但 `/health` 在上游检查结束前不发送响应 | 确认 |

#### 根因

本地存活与 OpenAI 模型就绪被合并到同一个 `/health` 路由。路由在返回本地状态前同步等待带五秒超时的模型元数据请求；Friday 客户端和管理脚本自身又使用更短超时，因此会先中止并把“上游暂不可达”表现成“本地服务未连接”。

#### 解决方案

- `/health` 只读取本地诊断状态，返回 `upstream_status: "unchecked"`，不访问 OpenAI。
- 新增 `/ready`，只在有边界超时的模型元数据检查通过后返回 ready。
- Friday 客户端改用 `/ready`，因此不会把本地进程存活误报为 Live 可用。
- `npm start` 用 `/health` 判断服务是否已经监听；`npm run status` 和 `doctor` 分开报告本地与模型状态。
- 上游就绪默认三秒超时；成功与失败结果继续使用短期缓存，检查不会创建 Realtime 凭证或模型回复。

#### 验证结果

- 后端假上游测试 `10/10` 通过，包含上游延迟时 `/health` 仍快速返回、`/ready` 有界失败、状态命令分层输出和错误脱敏。
- Swift 客户端定向测试通过，确认模型就绪客户端使用 `/ready`。
- 真实本地服务中，`/health` 约 `6ms` 返回 HTTP 200；当前 OpenAI 网络不可达时，`/ready` 约 `3.0s` 返回 HTTP 503 和脱敏恢复提示。
- `npm run status` 同时输出“Local service: listening”和“OpenAI models: unavailable”，不再混淆两层状态。
- 未创建 Realtime 凭证，未发送音频，也未触发付费模型响应。
- 当前网络路由仍未恢复，因此没有在本轮验证 `/ready` 的真实 HTTP 200；成功路径已由本地假 OpenAI 上游覆盖。

#### 经验与后续

- 进程存在不是服务健康证据，交付检查必须使用有超时的应用层健康请求。
- Liveness 和 Readiness 是不同契约：前者回答进程能否服务，后者回答关键外部依赖能否完成产品请求。
- 客户端超时必须大于服务端上游超时，否则服务端准备好的错误信息会被客户端提前丢弃。
- 自动交付报告继续分开说明“本地服务已监听”和“OpenAI 模型已就绪”，任何一层都不能代替另一层。

### FRD-20260803-002：可撤销输入框写入的确认边界调整

- 状态：`待验证`
- 首次发现：2026-08-03
- 最近更新：2026-08-03
- 影响范围：Talk、Agent、Platform、权限与数据安全
- 关联：GitHub Issue #4、Draft PR #5；`ConversationActionBridge`、`FocusedInputActionExecutor`

#### 用户现象与影响

Friday 需要从“只会对话和 Mock Work”进入第一条真实本地动作：用户用语音要求把确定文字写入当前输入框。第一版采用完整视觉预览和按钮确认，但产品评审认为这会让用户在已经明确说出“写入”后重复授权，破坏语音 Agent 的连续性。新的问题是：如何去掉低风险动作确认，同时不让模型误解、重复事件或焦点变化造成错误写入。

#### 环境与复现

- macOS 14.0+ 原生 App，Accessibility 写入使用现有剪贴板与 `Cmd+V` 路径。
- Talk 默认未配置额外收费的 final ASR。
- 最小场景：启动 Talk 时聚焦一个非密码输入框，用户要求写入一段确定文字。

#### 证据

- Realtime Function Call 只证明模型选择了工具，不能证明用户授权了具体副作用。
- 现有 Accessibility 服务可以锁定 AX 元素并在写入前恢复焦点，但不能由模型持有或选择 AX 句柄。
- WorkDraft 的语音确认依赖 final ASR；默认关闭时不能安全创建正式后台 Work。
- Issue #4 最初要求完整视觉预览和按钮决策；2026-08-03 产品决策将范围改为只对锁定目标上的可撤销本地写入自动执行。
- 当前自动测试不连接 Realtime、不操作真实输入框，也不包含用户正文日志；真实 Mac 证据仍待补充。

#### 假设与实验

| 假设 | 验证方式 | 结果 | 结论 |
| --- | --- | --- | --- |
| 任意 Realtime 工具调用都可以直接授权写入 | 对照意图、风险和目标约束 | 工具必须仅暴露明确写入意图，并在本地验证风险、策略和锁定目标 | 排除无边界自动执行；保留受限自动执行 |
| 没有 final ASR 时必须隐藏所有动作工具 | 区分正式后台 Work 和可撤销前台动作 | 后台 Work 仍依赖 final ASR；前台写入可由明确工具意图、目标锁定和系统撤销构成独立边界 | 对前台可撤销写入排除；后台 Work 仍保留此要求 |
| 确认时重新使用当前焦点即可 | 用户收起岛、切换窗口后比较目标身份 | 当前焦点可能已变，会把内容写到意外控件 | 排除，必须复验 Talk 启动时锁定的目标 |
| 一个随机 WorkID 等同于完整 Work | 对照 Work Store 和恢复契约 | 当前没有对应持久化 WorkRecord、状态机或恢复记录 | 排除；只标记为会话内 foreground action work scope |
| 可撤销意味着不需要任何约束 | 检查误触、重复事件和密码框风险 | `Cmd+Z` 只能降低后果，不能阻止写错目标或重复写入 | 排除；仍需非密码目标、revision 复验、幂等和串行执行 |

#### 根因

这是风险分级和交互边界设计问题，不是单一代码缺陷。初始方案把“会修改内容”统一等同于“必须二次确认”，没有区分可撤销的本地输入与发送、提交等高风险外部副作用，因而产生了不必要的交互摩擦。去掉确认也不能把模型工具调用直接视为无条件授权，必须由本地策略验证目标、风险、撤销和幂等条件。

#### 解决方案

- Realtime 只在用户明确表达“写入、放入、填入当前输入框”时调用 `write_focused_input`，参数必须包含完整最终文字；起草、改写、翻译和总结仍直接回答。
- Friday.app 在 Talk 启动时本地锁定非密码输入目标，把随机 target revision 附加到 `ActionProposal`；模型不接触 AX 句柄。
- `ConversationActionBridge` 只接受 `reversibleLocalWrite + automaticWhenTargetLocked`，同一时刻串行执行一项本地动作，并按 Tool Call ID 缓存 ActionReceipt，避免相同调用重复写入。
- `FocusedInputActionExecutor` 执行前复验原目标 descriptor，只调用一次现有可撤销剪贴板写入路径，并返回 `succeeded / failed / unknown`。
- 成功写入不打开确认或完成界面；失败和 `unknown` 只显示不含正文的轻量提示，不结束 Talk。
- 用户已经开始新一轮说话、续句 Response 已排定或模型正在回应时，工具结果使用 `createsResponse=false` 回到对话上下文，避免额外口头 Response 抢话。
- 当前 WorkID 只用于会话内 Proposal 与 Receipt 关联，不写成持久化 WorkRecord；发送、提交、发布、购买、删除、权限变更、文件、浏览器和坐标动作不在自动范围内。

#### 验证结果

- 8 条 Swift Agent 定向测试通过，覆盖自动执行、完成后重复 Tool Call 不重写、单动作串行、无目标和空文字零执行、目标 revision 变化、未知回执以及 Talk 连续性。
- Coordinator 集成测试覆盖自动写入时 Talk 保持连接，以及用户正在说话时不创建并发跟进 Response。
- Backend 假上游契约测试 `10/10` 通过，覆盖无 final ASR 时保留受限自动写入工具但不暴露后台 Work 工具。
- 完整零费用门禁通过：Backend 假上游测试 `10/10`；Swift 测试 `108` 条通过，`1` 条真实音频硬件测试按默认策略跳过；签名 Debug 测试构建、Swift 类型检查、`Info.plist`、`project.pbxproj`、Node 语法和差异检查通过。
- 新 Backend 已在 `127.0.0.1:8787` 监听，`/health` 显示 Prompt `focused-write-v2`、`automatic_focused_write_enabled=true` 与 `automatic_reversible_write` 已生效。当前网络路由无法完成 OpenAI 模型元数据检查，按开发约定只记录为环境状态，不作为本次代码故障。
- 自动检查没有创建 Realtime 凭证、发送音频或触发付费模型响应。真实 Mac TextEdit 与 Web/Electron 写入、`Cmd+Z`、目标失效和真实 Talk 连续性仍未验收，因此状态保持 `待验证`。

#### 经验与后续

- “模型意图”“本地执行策略”“系统执行”“可观察结果”必须用不同类型和状态表达；自动策略不是跳过本地安全判断。
- 可撤销允许降低确认摩擦，但不能替代目标锁定、密码框排除、幂等、串行和结果回执。
- 临时 ID 可以建立会话内关联，但不能冒充持久化 Work、权限或审计账本。
- 下一步先完成真实 Mac 验收，再把需要确认的高风险 Permission 和 Receipt 接入持久化 Work/Delivery；不能把当前自动策略直接扩展到发送和提交。
