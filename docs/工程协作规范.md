# Friday 工程协作规范

> 版本：0.3 · 日期：2026-08-03

这份文档定义产品负责人和 Codex 在 Friday 项目中的工作方式。它是人读的协作约定；代码任务的强制规则见仓库根目录 `AGENTS.md`。

## 1. 双方角色

### 产品负责人

- 决定用户是谁、先解决什么问题、哪些行为可以自动执行。
- 决定隐私、供应商、成本、定价和公开发布范围。
- 对无法从代码或文档推断出的产品选择做最终确认。
- 在真实 Mac 上完成权限、语音、跨应用行为和安装体验的人工验收。

### Codex

- 读取最新工程和文档，提出可验证的实现方案。
- 在用户授权范围内直接修改代码和文档。
- 识别不确定性、风险和未覆盖的边界，不把猜测写成事实。
- 运行适合当前风险的检查，并报告证据、失败原因和人工验证项。
- 不擅自购买服务、提交外部表单、推送代码或发布版本。

## 2. 准确性与证据规则

- 产品负责人和 Codex 的判断都不是天然正确；争议以可复现行为、源码、工程配置、测试结果和官方一手资料为准。
- 每次结论标明它属于产品设想、当前实现、自动验证结果还是人工验收结果。
- 价格、模型能力、API 字段、macOS 权限规则等会变化的信息，需要注明来源和查询日期；不能只依赖历史对话或二手文章。
- 如果用户描述与仓库现状不一致，先列出差异和证据，再决定是否修改，避免把正确代码改成错误假设。
- 如果无法获得足够证据，选择影响范围最小且可撤销的实现，并把假设写进交付说明。

证据优先级通常为：

```text
真实 Mac 可复现结果
→ 自动测试与构建输出
→ 当前源码和工程配置
→ 官方文档与供应商响应
→ 项目文档和历史讨论
→ 尚未验证的推测
```

## 3. 需求进入实现的顺序

每个新能力尽量按以下顺序推进：

```text
用户问题
→ 用户故事
→ 验收条件
→ 技术方案
→ 小步实现
→ 自动检查
→ 真机人工验收
→ 更新路线图、决策记录和必要的工程复盘
```

小修复可以直接实现，但只要改变用户可见行为、权限边界、数据流、供应商或版本承诺，就要先更新路线图或决策记录。

### 工程问题复盘

遇到反复出现、跨模块、难以直接定位，或涉及音频、异步状态、权限、网络、隐私、费用与数据安全的问题时，Codex 在排查开始时建立《工程问题与复盘》条目，并随着证据更新。

- 先记录用户现象和第一手证据，再记录技术假设。
- 保留被排除的关键方向和无效实验，说明为什么不成立。
- 根因、修复和“已解决”状态必须分别有证据，不能互相替代。
- 记录应提炼成不了解上下文的人也能理解的案例，但不得包含密钥、用户内容、原始语音或完整截图。
- Issue、PR、路线图决策记录和工程复盘各自承担不同职责，必要时通过编号或链接关联。
- 问题尚未解决时也要保留“调查中”记录和下一步，不为了完整性编造结论。

## 4. 讨论与沟通格式

- 默认使用中文；先说结论，再说理由和影响。
- 工具工作超过一小段时间时，说明正在检查什么、学到了什么、下一步是什么。
- 开始编辑前说明将修改哪些文件和行为。
- 完成后说明：改了什么、验证了什么、还需要用户做什么。
- 不确定时明确写出假设；若不同选择会明显改变产品，先请求确认。
- 不用“已经支持”描述尚未在真实 Mac 上验证的能力。

## 5. 允许直接做与必须确认

### 默认可以直接做

- 读取仓库文件、工程配置和日志。
- 修改 Friday 范围内的代码、测试和文档。
- 运行本地构建、单元测试、静态检查和 Mock 流程。
- 创建本地 Mock 数据、测试夹具和可恢复的临时文件。

### 必须先确认

- 购买 API、服务器、域名、Apple Developer 服务或第三方中转服务。
- 使用或提交真实 API Key、麦克风录音、屏幕截图、个人文件或账号凭证。
- 发送邮件、提交表单、删除数据、修改系统设置或执行不可逆动作。
- `git push`、发布 DMG、上传 TestFlight 或对外发布版本。
- 将产品范围扩大到 Windows、移动端、持续屏幕监控或高风险 Agent。

## 6. 代码工作规则

- 优先保持现有结构，不为了“看起来更完整”提前搭建无用途的抽象。
- macOS 系统能力放在 Platform 层；UI 不直接管理 Accessibility、音频流、截图和网络凭证。
- 模型调用放在 Provider/Service 层；界面只消费状态和结果。
- Realtime Provider 必须保留 Mock Provider，UI 不应该因为没有 API Key 就无法开发。
- 任何会产生外部副作用的工具都需要显式风险等级、参数预览和确认策略。
- 共享逻辑出现第三次重复时再抽象；两次重复先保持简单。
- 单个 Swift 文件超过 800 行时，新增功能前先评估拆分；超过 1200 行原则上必须拆分。
- 新增 Swift、MJS 和 Shell 源码按《编程 Agent 规范》写完整的“功能 / 职责 / 边界”文件头。

## 7. Friday 的建议目录边界

目标边界和迁移顺序以《技术架构》为准。当前迁移期间遵守下面的依赖方向，不为目录外观一次性搬动已工作的代码：

```text
Friday/
├── App/              应用入口、菜单栏和生命周期
├── Features/         Dictate、Talk、Agent 等用户能力
├── Runtime/          Conversation、Work、Permission、Delivery 编排
├── Platform/         Accessibility、Hotkey、ScreenCapture、Audio、ActionExecutor
├── Providers/        Realtime 与 Agent Backend 的可替换实现
├── Core/             身份、Context、共享状态和错误
├── Shared/           共享模型、设计组件和格式化工具
└── Resources/        本地化、图标和静态资源
```

当前项目还处于骨架阶段，不需要为了遵守目录图立即搬迁所有文件；只有新增能力进入实现时，才按该边界放置。

依赖方向固定为：Features 依赖 Runtime 契约，Platform 和 Providers 实现 Runtime 端口，Core 不反向依赖 UI 或具体 Provider。Dictate、Talk 和 Agent/Work 使用不同生命周期，不能合并成一个巨型工作流状态。

## 8. 数据与安全红线

- OpenAI 或其他供应商的长期 API Key 只能留在服务端，不能进入 `.app`、UserDefaults 或日志。
- 客户端使用短期凭证建立 Realtime 会话。
- 默认不持续读取屏幕；屏幕捕获必须由用户主动触发。
- 原始音频、截图、完整转录和输入内容默认不写入普通日志。
- 本地缓存用户内容前必须说明保存目的、保留时间和删除入口。
- Agent 工具调用按风险分级：只读、可撤销写入、外部副作用、不可逆操作。
- 发送、删除、购买、提交和权限变更默认需要用户确认。
- 第三方中转站不能成为不可替换的核心依赖，Provider 接口必须可切换。

## 9. 测试与验证标准

### 自动检查

日常功能迭代默认运行一次构建，并只执行与本次行为直接相关的测试。UI 修改还要做对应状态的实际窗口截图或真机观察；测试数量不能替代交互验收。

Prompt 和语音交互处于快速迭代期时，默认采用以下最小验证闭环：

1. 只运行覆盖本次 Prompt payload、工具描述或事件契约的聚焦测试。
2. 纯后端 Prompt 修改不运行完整 Swift 测试；修改 Swift Provider 或交互代码时只补一次 Debug 构建。
3. 重启本地语音服务，并通过健康检查中的 Prompt 版本确认新代码已经加载。
4. 提供 3 至 5 条固定真机口述脚本，由产品负责人检查语言、意图、工具选择和自然度。
5. 只有共享底层、提交前、发布前或出现跨模块回归时才运行完整 `verify.sh` 或完整测试套件。

完整测试门禁用于共享底层改动、跨模块风险、发布候选或用户明确要求，不作为每次细节调整的固定动作：

```bash
xcodebuild -project Friday.xcodeproj -scheme Friday -configuration Debug -destination 'platform=macOS' build
xcodebuild test -project Friday.xcodeproj -scheme Friday -destination 'platform=macOS'
```

当前只有 Demo 时，至少验证 Swift 语法和 `Info.plist`；不能因为缺少完整 Xcode 就声称构建通过。

### 手工验证

- TextEdit、备忘录、Safari 搜索框至少各验证一次输入注入。
- 权限拒绝、无焦点、目标应用退出和网络断开必须各有一条可观察结果。
- 语音和屏幕能力必须在真实 Mac 上验证，不能只用 SwiftUI Preview 代替。
- Talk 声学交互至少覆盖：用户安静时完整播放、用户中途插话、回复结束后立即接话、内置扬声器回声和音频设备切换。
- 框选交互至少覆盖：屏幕不变暗、提示跟随鼠标、四角不裁切、最小选区、`Esc` 取消和框选失败后 Talk 仍可继续。
- 改 UI 时同时检查窄窗口、浅色/深色模式、菜单栏展开和主窗口状态。
- 改 Agent 时必须检查取消、暂停、重试、确认和错误恢复。

## 10. Git 与版本边界

- 不修改用户已有的无关改动。
- 不执行 `git reset --hard`、`git checkout --` 或大范围删除。
- 未经明确要求不执行 `git push`。
- “先保存、先同步、先收尾、先提交”不等于允许推送。
- 用户明确要求发布版本时，才执行签名、公证、DMG 和发布检查。
- 文档与代码同时变化时，最终说明两者的影响范围。

## 11. 完成定义（Definition of Done）

一个 Friday 功能只有同时满足以下条件，才可以说“完成”：

- 用户故事和验收条件已明确，或明确记录为工程任务。
- 实现放在正确的模块边界内，没有把系统权限或凭证逻辑塞进视图。
- 有对应的 Mock、单测、集成检查或真机验收记录。
- 失败、取消、权限拒绝和无目标状态有清晰反馈。
- 没有新增未说明的隐私、费用或外部副作用。
- 路线图、决策记录或 README 已同步到最新状态。
- 最终回报包含验证结果和剩余风险。

## 12. Issue 与 PR 管理

Friday 使用 Issue 记录问题、范围和验收条件，使用 PR 记录实现、证据、审查和回滚边界。详细规则与模板见《Issue 与 PR 工作流》：

- 新功能、用户行为、Bug、架构、隐私、权限和费用调整必须先有 Issue。
- 纯注释、错别字或极小文档修正可以不建 Issue，但 PR 必须说明豁免理由。
- 一个分支只服务一个 Issue；一个 PR 只交付一个可独立验收和回滚的结果。
- PR 使用 `Closes #<issue>` 关联 Issue，并区分实现、自动检查和真实 Mac 验收。
- 基线建立后不直接在 `main` 开发；紧急例外需要产品负责人明确批准并补齐记录。
- Issue、PR、推送和合并属于外部操作，Codex 只有在用户明确授权后才能执行。
