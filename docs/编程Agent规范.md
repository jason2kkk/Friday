# Friday 编程 Agent 规范

> 版本：0.1  
> 日期：2026-08-02  
> 适用范围：所有由编程 Agent 执行的源码新增、删除、重命名、职责调整和结构维护任务。

## 1. 规范定位

本规范用于保证代码实现、文件头说明和《项目结构》始终描述同一个工程事实。

仓库根目录的 `AGENTS.md` 是唯一强制规则入口；本规范是其中“源码文件说明与结构同步”规则的详细执行手册。两者冲突时以 `AGENTS.md` 和用户当前明确要求为准，并在本次任务中同步消除冲突。

## 2. 开始编码前

编程 Agent 在修改源码前必须：

1. 阅读 `AGENTS.md`、`docs/编程Agent规范.md`、`docs/Issue与PR工作流.md` 和 `docs/项目结构.md`。
2. 阅读将要修改的源码文件及其直接依赖，不能只根据文件名或历史对话推测职责。
3. 确认本次变化属于“实现细节变化”还是“文件职责变化”。职责变化包括能力、所有权边界、主要依赖、数据流、权限、隐私或外部副作用发生变化。
4. 功能、Bug 或架构任务开始前确认对应 Issue 和独立分支；没有外部操作授权时不虚构 Issue 编号。
5. 开始编辑前向用户说明代码、文件头和结构文档的预计修改范围。

## 3. 源码文件头

### 3.1 适用文件

仓库维护的 Swift、JavaScript 和 Shell 源码文件都必须有文件级说明：

- `*.swift`
- `*.mjs`
- `*.sh`

配置、测试夹具、Markdown 和 Xcode 工程文件不强制使用源码文件头，但仍应在 `docs/项目结构.md` 中有简要职责说明。

### 3.2 固定格式

Swift 和 JavaScript 文件在第一个 `import` 之前写：

```text
// 功能：说明该文件向产品、系统或开发流程提供的完整能力。
// 职责：说明它管理的关键流程、状态、数据或依赖，以及主要输出。
// 边界：说明它明确不负责的工作、禁止的副作用或必须委托的下游模块。
```

Shell 脚本必须保留 shebang 在第一行，紧接着写：

```sh
#!/bin/zsh
# 功能：说明脚本提供的完整能力。
# 职责：说明它编排的关键命令、输入和输出。
# 边界：说明它不会执行的外部操作、付费调用或真机行为。
```

### 3.3 内容要求

- `功能` 回答“为什么存在这个文件”，不要只把文件名翻译成中文。
- `职责` 至少覆盖主要流程或状态、关键依赖、主要输入输出中的两项。
- `边界` 明确模块边界；涉及 API Key、用户内容、音频、屏幕、系统权限、网络、付费模型或外部副作用时必须明确写出。
- 注释只描述当前代码已经承担的职责，不把路线图目标、未接入能力或推测写成已实现事实。
- 注释保持文件级视角，不逐个复述类型、函数或每行实现。
- 测试文件要说明覆盖范围，并明确是否依赖真实权限、硬件、网络或付费模型。

## 4. 必须同步更新的场景

| 代码变化 | 文件头 | `docs/项目结构.md` | 其他必要动作 |
| --- | --- | --- | --- |
| 新建源码文件 | 新增完整“功能 / 职责 / 边界” | 新增文件路径和一句职责 | Swift 文件按需加入 Xcode Target |
| 删除源码文件 | 删除文件 | 删除对应条目 | 清理工程引用和直接文档链接 |
| 重命名或移动文件 | 检查并更新 | 更新路径和目录 | 同步工程引用与 import/调用位置 |
| 文件主要职责变化 | 更新三行说明 | 更新一句职责 | 检查模块边界、测试和架构文档 |
| 仅实现细节变化，职责未变 | 通常不改 | 不改 | 避免为了制造改动而重写文案 |
| 新增配置、夹具或工程文件 | 不强制源码文件头 | 新增简要条目 | 说明生成方式或维护归属 |

“代码已经能运行”不代表同步完成。只要文件头或项目结构仍描述旧职责，本次代码任务就未达到交付标准。

## 5. 编程过程中的维护规则

- 新能力优先放入职责匹配的现有文件；文件开始同时承担第二个独立模块时，应先评估拆分。
- 修改过程中发现实际职责与原文件头不一致时，以源码证据为准修正文案，并检查《项目结构》是否也已过期。
- 用户或其他并发任务新建文件时，不能覆盖或删除；应读取最新内容后将其纳入结构索引和文件头检查。
- 文件移动不得只追求目录外观，必须同时满足 `AGENTS.md` 的架构边界和现有依赖方向。
- 文件头不记录日期、作者、临时任务状态和容易过期的实现数字；这些内容应进入路线图、验收文档或版本历史。

## 6. 交付前检查

编程 Agent 至少确认：

1. 本次涉及的每个源码文件都有准确的“功能 / 职责 / 边界”。
2. 所有新增、删除、移动或职责变化都已同步到 `docs/项目结构.md`。
3. `README.md` 或 `docs/README.md` 已为新增的长期文档提供可发现入口。
4. 注释没有把计划、自动检查或未经真机验证的行为写成事实。
5. 最终回复明确说明文件头和结构文档是否同步，以及哪些验证按用户要求未执行。
6. 最终回复说明 Issue、分支、提交和 PR 的实际状态，不把“待创建”描述成已经创建。

注释和结构文档的同步检查不能替代代码测试；反过来，构建或测试通过也不能替代这项文档同步。
